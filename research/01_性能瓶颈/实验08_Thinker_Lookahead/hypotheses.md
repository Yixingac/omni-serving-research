# 实验 8 的假设与判定标准（预先登记）

> 写于 2026-11-17 14:40（美东），在实验 8 的任何正式数据产生之前。

## 研究问题

实验 5 的 kernel trace 显示，thinker 每一步 GPU 算 23–25 毫秒，然后空 3–8 毫秒：CPU 先等 GPU 算完这一步，才准备下一步。源码里，要出语音的请求不能用“提前一步发射”。本实验要回答：
1. 同步执行造成了多少本来可以避免的空档？
2. 纯文字请求是不是真的用上了提前一步发射？
3. prefill 插进来时，提前发射是否经常被清空（flush）？
4. 语音请求能否安全地用上提前一步发射？
5. 如果改了，端到端到底能快多少？

## 从源码已经知道的事（sglang-omni 520b49ee，均为实测阅读）

- thinker 的调度循环是 `OmniScheduler.event_loop_async_decode`（`sglang_omni/scheduling/omni_scheduler.py` 第 3631 行起）。每一轮先取下一批：
  - 只有满足四个条件才走提前一步发射：这一批是纯 decode、请求数不低于下限、`lookahead_eligible` 为真、有批可跑。
  - 否则先把在途的那一步收尾（flush），再同步执行这一批。
  - 另外两种情况也会先 flush：有分块 prefill 正在进行；等待队列里有新请求而这一批还没满（mixed chunk）。
- `lookahead_eligible`（`sglang_omni/model_runner/thinker_model_runner.py` 第 495 行起）在以下任一情况返回假：
  - 有请求要出语音；
  - 要 logprob；
  - 采样参数里有重复惩罚、存在惩罚、频率惩罚、最少生成长度、固定种子、logit bias 或自定义参数。
- 源码注释给的原因：MiniCPM-o 的语音要在收尾时读 thinker 的 hidden state，而提前发射的下一步会把它覆盖。
- token id 已经用了两块 pinned 内存轮换（`async_host_buf`），让收尾第 N 步时，第 N+1 步写另一块。

## 第一阶段：不改执行逻辑的对照

### 设计

- **分工**：2+6。
- **对比两种负载**，用同样的提问、同样的生成参数（温度 0、最多 64 个 token）：
  - W3t：只要文字回答；
  - W3b：文字 + 语音回答。
- **负载**：闭环并发 8、32、64。
- **重复**：3 个区组。每个区组是一次独立启动的服务，区组内 6 个（负载 × 并发）组合的顺序随机，种子 20261117。
- **每个组合**：
  1. 先预热一波；
  2. 再测 max(96, 3×并发) 个请求，开事件记录（包括新增的 thinker 每步事件）；
  3. 再在同样负载下开 3 秒 kernel trace。
- **打点版 sglang-omni**：和实验 6 相同。thinker 每一轮记录：
  - 这一批的请求数、是 decode 还是 prefill；
  - 是否提前发射；不发射时是哪一条条件不满足；
  - 是否 flush 以及原因；
  - 发射、收尾、同步执行各花多少 CPU 时间。

### 主要指标

- **thinker 每一步的 GPU 空档**（毫秒）：kernel trace，用实验 5 的 `exp05_step_sync.py`。
- **“同步等完这一步才准备下一步”的步数占比**：同上。
- **thinker 每轮的提前发射比例和不发射的原因分布**：新增事件。

### 次要指标

thinker 每个 token 的时间、TTFT、端到端、flush 次数、prefill 轮占比、实际 batch 大小。

### 假设

- **H8a**：W3t 的 thinker 每一步大多走提前发射，每步 GPU 空档明显小于 W3b。
  - 支持：在 batch 大小相近（按每步事件的请求数分组）时，W3t 的空档中位数比 W3b 小一半以上。
  - 反驳：两者差不多。那么文字路径也被别的条件挡住了，事件里的原因字段会指出是哪一条。
- **H8b**：W3t 里还有一部分轮次因为 prefill 插入而 flush，并发越高越多。
  - 支持：flush 占轮次的比例随并发升高。

### 解释上的限制（预先写下）

- W3t 和 W3b 的 thinker 做的事情不完全一样：语音请求要多保存、多发送 hidden state。
- 同样的并发下，W3t 的请求不经过 talker，在 thinker 里待的比例更高，batch 会更大。
- 所以第一阶段的差别只能当作“提前发射最多能省多少”的上限估计，不能当作修改后的实际收益。

## 第三阶段：最小原型（只有第一阶段支持时才做）

- **进入条件（预先确定）**：同时满足以下两条，才做原型：
  - H8a 得到支持；
  - 按第一阶段的数据推算，W3b 每步能省下 ≥ 2 毫秒。
- **正确性要求（先写测试再改代码）**：
  - hidden state 不被提前覆盖；
  - 同一批里各请求不读错；
  - batch 大小变化、prefill 插入、flush 时对应关系不乱；
  - 文字、语音混合的批正确；
  - 输出 token 和语音的顺序不乱、不重复、不丢；
  - 无死锁、无非法内存访问。
- **对照方式**：
  - 输出对比：同样的输入、并发 1、温度 0，改前改后逐 token 比较文字，逐个比较语音编码 token。不假设 CUDA 路径一定逐位相同；如有差异，报告差异的数量和位置。
  - 性能对比：同一个 W3b 负载，改前改后，并发 8、32、64，3 个区组，区组内顺序随机。
- **主要指标**：
  - thinker 每步 GPU 空档；
  - thinker 每个 token 的时间；
  - 端到端 P50、P95、P99；
  - TTFT；
  - 显存增加量；
  - 同步调用次数；
  - 错误率。
- **判定**：
  - 正确性检查有任何一项不通过，就不报告性能收益，只保留失败证据。
  - 性能上，以 3 个区组配对差的方向和大小来判断，不声称统计显著。

## 补充登记（2026-11-17 14:58 美东，正式数据产生之前）

**为什么补充**：打点版冒烟测试（`exp06_smoke_instr`，不是正式数据）里，W3b 并发 16 的 1181 个纯 decode 步全部没用提前发射。每一步被挡的原因里，除了“语音”，还有“采样参数”。

**查到的原因**：
- 我们自己的压测客户端给每个请求都带了 `"seed": 0`（`src/omni_research/replay/backends.py` 的 `ModelRequest.seed` 默认值）。
- sglang-omni 的 `lookahead_eligible` 对带固定种子的请求一律走同步。
- 这和要不要出语音无关，所以纯文字请求也会被挡住。

温度为 0 时用的是贪心解码，种子不影响输出，所以去掉种子不改变生成结果。

**设计改动**：在原来的两种负载之外，加一个因素“请求带不带种子”，变成 2×2：

| 条件 | 负载 | 种子 | 预期被什么挡住 |
|---|---|---|---|
| w3t | 只要文字 | 带 `seed: 0`（原设计） | 种子 |
| w3t_ns | 只要文字 | 不带（`"seed": null`） | 无，应该走提前发射 |
| w3b | 文字 + 语音 | 带 `seed: 0`（原设计） | 语音、种子 |
| w3b_ns | 文字 + 语音 | 不带 | 语音 |

每个区组里 12 个（条件 × 并发）组合的顺序随机，种子仍为 20261117。

**新增的假设**：

- **H8c（主要）**：同为只要文字，w3t_ns 的 thinker 每步 GPU 空档明显小于 w3t。两者只差种子一项，所以这是提前发射本身效果的直接干预对照。
  - 支持：并发 8、32、64 下，空档中位数都至少减半，3 个区组方向一致。
  - 反驳：差别不到 1 毫秒，或方向不一致。
- **H8d（阴性对照）**：w3b 和 w3b_ns 没有差别，因为语音照样挡住提前发射。
  - 如果有差别，说明还有我们没认识到的机制。

H8a 原来比较的是 W3t 和 W3b（都带种子）。按上面查到的原因，预期两者都走同步、差别很小。这一条照原计划报告，不删除。

**第三阶段的进入条件（同一次补充登记，15:32 补写，实验 8 仍没有任何数据）**：
- 原来写的是“H8a 得到支持”。补充登记后，H8a 的两边都带种子，比较的已经不是提前发射本身。
- 改为同时满足以下两条才做原型：
  - H8c 得到支持；
  - 按第一阶段的数据推算，语音请求如果也能提前发射，每步能省下 ≥ 2 毫秒。推算方法是：w3b_ns 的每步空档减去 w3t_ns 的每步空档，在批大小相近时比较。
