# 实验 7：限制、失败和偏离

按“对结论影响多大”排序。README 里的方案 A–E 和配置名的对应见 README 文末。

## 1. 机制对照的两边用的卡数不同

- 方案 E（t2_k3_shared）用 5 张卡，方案 C（t2_k3_c3）用 8 张卡。
- 所以机制判断（H7a）只看“处理时间”：talker 生成每秒语音的时间、code2wav 同形状批的 GPU 时间、kernel 同时在跑的时间。
- 排队和端到端的差别里混有“多了 3 张卡”的容量差别，不用来判断机制。
- talker 的处理时间还和它同时处理的请求数有关。README 6.1 用 Little 定律在“同时处理的请求数差不多”的条件下做了对照：
  - 这是推算：每个请求在 talker 里的平均时间，用“每秒语音时间的均值 × 平均语音秒数”近似，不是逐个请求直接求和。

## 2. 等预算对照分不开两种原因

- 同样 8 张卡，把 code2wav 搬走的同时，talker 的副本数也变了（6 → 4、3、2）。
- 吞吐的差别里，“不再抢卡”和“talker、code2wav 的卡数比例变了”两种原因混在一起，本实验分不开。
- README 6.2 的“每张 code2wav 卡约 6 请求/秒、同卡约 3.7”是推算：并发 256 的吞吐 ÷ code2wav 的卡数，前提是 code2wav 是瓶颈（排队长、卡忙 86–91%）。

## 3. 开环速率由最弱的方案决定，测不到强方案在高负载下的延迟差别

- 正式速率（5.5、8、9.5、10.5 请求/秒）按事先定好的方法，从预跑里最弱的等预算方案（B，10.6 请求/秒）算出。
- 这些速率只有 A、D 容量（约 22–24）的一半左右。所以：
  - 开环正式速率下，A、C、D 都离容量很远，延迟差别都在 5% 以内；
  - 高负载下的尾延迟差别只能从闭环（并发 128、256）和探索性速率看。
- H7c 的“接近容量时差别变大”因此只测到了 B 的一侧，没有测到 A、D。
- 15、18 请求/秒是看过预跑后才加的，只用来描述，不参与判定。

## 4. 高负载下“批大小为 1 的批”很少

- H7a 的 code2wav 指标用批大小为 1 的批。并发 128、256 时大多数批都更大：
  - 每个运行里单个请求的批只有 2–42 个；
  - 方案 C 每档只有 3 个，方案 E 3–11 个。
- H7a 被判为“不确定”的那一项（并发 256 的 flow 每帧时间，区组 1 只短 7.6%），就是 E 只有 11 个、C 只有 3 个批的格子。
- 描述性指标“code2wav 每秒语音的 GPU 时间”用了所有批，结论方向相同（同卡多 49–59%）。

## 5. 判定用的吞吐在低负载时受尾巴影响

- 吞吐 = 成功请求数 ÷（最后一个完成 − 第一个发出）。并发 8 时一档只有 96 个请求，最后几个慢请求会明显拉长分母。
- 例如方案 A 的区组 1 在并发 8 有一个 P99 4.5 秒的尾巴，吞吐 3.25，另两个区组 3.56、3.43。
- H7c 的“并发 8 时差别 < 5%”因此没有通过（B +11.4%，区间 [−5.1, +27.8]）。按登记的规则如实判为“不支持”。

## 6. kernel trace 只有 3 秒、只在并发 128

- 重叠比例只代表并发 128、这 3 秒内的情况。
- 窗口长度按 kernel 的最早开始到最晚结束算，各卡是 1.6–3.1 秒（profiler 开 3 秒，但有的进程最后一段没有 kernel）。
- 本实验 15 次运行的 kernel trace 段都没有让 code2wav 崩溃（实验 6、实验 8 第一阶段里开 profiler 的段崩过 4 次）。所以结果里没有“重启之后”的档位。

## 7. 部分描述性指标是看过第一遍结果后才加的

- talker → code2wav 的传递时间、code2wav 每秒语音的 GPU 时间、thinker 每个 token 的时间、SM 时钟和功耗，都是第一遍分析之后才加进 `exp07_report.py` 的。
  - 原因是任务要求测这些量，第一遍的脚本没有算。
  - 加的时候先写测试、确认失败，再写实现。
- 它们不参与判定。加完之后重跑，三个假设的判定和第一遍完全相同（逐字段比较）。
- 没有记录 GPU 温度。nvidia-smi 的采样里有 SM 时钟和功耗，见 README 6.1。

## 8. 没有测的东西

- **talker 单卡的容量**：README 7.2 的“D 可能接近最优”没有验证。
- **其他负载**：只测了 W3b 的短回答（最多 64 个文字 token、平均约 13 秒语音）。回答更长时，talker 的工作更多，D 只有 2 份 talker 的代价可能更大。
- **其他放置**：例如“talker 1 张 + code2wav 5 张”，或者部分 code2wav 同卡、部分独占。

## 9. 运行上的情况

- 15 次运行都一次成功，没有服务重启、没有错误。
- 区组 3 的方案 A 启动用了 600 秒（其他 95–325 秒）。日志显示时间花在从 NFS 加载模型和导入，没有超时（上限 2400 秒）。测量在服务就绪之后才开始，不影响结果。
- 运行期间集群上的研究仓库做过几次 `git pull --ff-only`，改的都是分析脚本、文档和后续实验的配置，压测客户端和编排代码没有变（记录在 Job 的 code_state.txt；metadata.json 列出了每次运行开始时的提交）。
