## 研究问题

把 code2wav 从 talker 的卡上搬到单独的卡上：
1. 资源争用会不会减少？
2. 单个阶段会不会变快？
3. 在同样 8 张卡的预算下，整个系统的吞吐和尾延迟会不会改善？

## 两种对照，回答的问题不同

| 对照 | 方案 | 只改了什么 | 能回答 | 不能回答 |
|---|---|---|---|---|
| A：机制验证 | `t2_k3_shared`（2 张 thinker 卡 + 3 张卡上 talker 和 code2wav 同卡，共用 5 张卡，GPU 5–7 空着）对比 `t2_k3_c3`（2 + 3 张 talker 卡 + 3 张 code2wav 卡，用满 8 张） | code2wav 和 talker 是否同卡。两边副本数都是 thinker 2、talker 3、code2wav 3 | 同卡争用是否存在、有多大 | 哪种部署更划算（两边用的卡数不同：5 对 8） |
| B：等预算部署 | `t2_k6_shared`（2+6，基线）、`t2_k4_c2`、`t2_k3_c3`、`t2_k2_c4` | 8 张卡怎么分给 talker 和 code2wav | 同样 8 张卡，哪种放置的吞吐和尾延迟更好 | 差别有多少来自“不再争用”，有多少来自“副本数和卡数比例变了”（两者在这里分不开） |

## 实验单位和设计

- **实验单位**：一次独立启动的服务。
- **区组设计**：随机完全区组。每个区组把全部方案各跑一次，区组内的顺序随机（种子 20261117）。共 3 个区组，同一台节点，依次进行。
- **每次运行**：
  - 闭环并发 8、64、128、256，每档先预热一波，再测 max(96, 3×并发) 个请求，开事件记录；
  - 开环泊松到达，4 个共同速率，每个速率 90 秒，开事件记录；
  - 并发 128 时开 3 秒 kernel trace，用来测同卡争用。
- **开环速率的定法（预先确定）**：
  - 先用预跑的闭环并发 256 吞吐，估出 B 组里最弱方案的容量 X；
  - 正式速率取 0.5X、0.75X、0.9X、1.0X，四舍五入到 0.5 请求/秒；
  - 所有方案用同一组速率。
- **软件**：和实验 6 相同的打点版 sglang-omni（同一提交 520b49ee 加打点补丁），才能把 code2wav 的排队和计算分开。基线方案在实验 6 里也用这个版本测过，可以互相核对。

## 主要指标

| 指标 | 用在哪个对照 |
|---|---|
| 闭环每档的吞吐（成功完成的请求/秒、语音秒/秒） | B |
| 开环各速率下端到端 P50、P95、P99，以及 TTFT | B |
| talker 每秒语音的生成时间、code2wav 每批的 GPU 跨度（同形状 batch） | A |
| kernel trace 里 talker 与 code2wav 同时在跑的时间比例 | A |
| 各阶段排队时间、talker → code2wav 的传递时间 | A、B |
| 每张卡的忙碌比例、显存 | A、B |

## 假设与判定

### H7a（机制）：同卡时 talker 和 code2wav 互相拖慢；分开后，同形状 batch 的 code2wav GPU 跨度和 talker 每秒语音的时间都会变短

- **支持**：在并发 128、256，`t2_k3_c3` 比 `t2_k3_shared` 短 10% 以上，3 个区组方向一致。
- **反驳**：差别在 ±5% 以内，或者方向不一致。
- **注意**：`t2_k3_c3` 多用了 3 张卡，排队时间的差别会混入容量的差别。所以机制判断只看“处理时间”（GPU 跨度、每秒语音时间），不看排队和端到端。

### H7b（部署）：同样 8 张卡，把 code2wav 单独放在一部分卡上，整体吞吐和高负载尾延迟都比 2+6 同卡更好

- **支持**：至少一个隔离方案满足两条：
  - 闭环并发 256 的吞吐比 2+6 高 10% 以上；
  - 开环 0.9X 速率下 P95 端到端更低。
  - 并且 3 个区组方向一致。
- **反驳**：所有隔离方案的吞吐都不高于 2+6，或者只在部分区组更高。
- **替代解释（预先写下）**：同卡时，talker 和 code2wav 可以互相填补对方的空闲，一张卡被用得更满。分开后，talker 卡和 code2wav 卡各自会有空着的时候，可能抵消“不争用”的好处。所以即使 H7a 成立，H7b 也可能不成立。

### H7c：隔离的收益随负载变化

- 低负载（并发 8）时各方案差别很小（< 5%），差别主要出现在接近容量时。
- 用开环 0.5X 和 0.9X 两个速率下的端到端差别来判断。

## 统计分析（预先确定）

- **单位**：以运行为单位汇总。每个方案、每个区组得到一个数，用区组内的配对差（方案 − 基线）计算。
- **报告**：
  - 3 个配对差的原始值、均值；
  - 基于 t 分布的 95% 置信区间（自由度 2）；
  - 相对改善百分比。
- **样本量**：只有 3 个区组，不声称统计显著，主要看方向是否一致、效应有多大。
- **排除规则**：
  - 预热不计；
  - 错误率超过 5% 的档位标为“不可用”，照样报告；
  - 服务启动失败或运行中崩溃的方案，记录为失败。这种情况可以补跑一次，但原来那次也要报告。
