# 实验 6：限制、失败和偏离

按“对结论影响多大”排序。每条写明：是什么、证据、对结论的影响、以后怎么改。

## 1. 开 torch profiler 时，code2wav 进程崩溃了 3 次

**是什么**：开 profiler 的 C 段里，code2wav 进程三次以段错误退出（退出码 −11）：

| 区组 | 段 | 崩溃的进程 | 报错的请求 |
|---|---|---|---|
| 1 | 并发 64 的 C 段 | code2wav@r1 | 13 / 192 |
| 2 | 并发 128 的 C 段 | code2wav@r1 | 149 / 384 |
| 3 | 并发 128 的 C 段 | code2wav@r0 | 32 / 384 |

实验 8 第一阶段（同一个打点版副本、同样的 profiler 窗口）在区组 1 的 W3b 并发 64 的 C 段也崩了一次（code2wav@r4，22 个请求报错）。

**证据**：
- 4 次都只发生在开 profiler 的 C 段，崩溃的都是 code2wav 进程，日志里没有 Python 调用栈。
- 不开 profiler 的段一次也没有崩：本实验 24 段 A/B，加上实验 8 第一阶段 18 段带语音的 B 段。开 profiler、带语音的 C 段共 30 段，崩了 4 次。
- 时间上：同一段里，其余 code2wav 进程的 trace 文件写完后 2–12 秒，崩溃的那个进程才退出，而且它自己的 trace 文件都没有写出来。
- **推断**（没有证实）：崩溃和 profiler（kineto/CUPTI）结束时导出 trace 有关。我们没有拿到原生调用栈，也没有专门复现。

**对结论的影响**：
- 这 3 段的客户端指标（吞吐、错误）不能用。第六部分开销表里，C 段对 A 段的吞吐下降，在并发 64、128 两档因此被放大，README 已注明并给出不含崩溃段的数。
- 这 3 段里崩溃进程的 kernel 统计缺失，图 6 的统计用其余 5 个 code2wav 进程。
- 崩溃后服务器被自动重启，后面的段在新服务上跑，每段各有一波预热。
- **拆分结论不受影响**：时间拆分来自 B 段，正式性能来自 A 段，这两种段都没有出现崩溃。

**以后怎么改**：实验 8 第三阶段加了一个测量开关（SGLANG_OMNI_EXP_TORCH_SKIP），只给要研究的进程开 profiler。如果要研究 code2wav 的 kernel，应改用 nsys，或者先单独复现这个崩溃。

## 2. 开 profiler 本身让系统明显变慢

- **证据**：同一区组内，C 段对 A 段的吞吐变化如下（括号外是含崩溃段的 3 个区组均值，括号内是不含崩溃段的值）：
  - 并发 8：−13%；
  - 并发 64：−39%（−31%、−41%）；
  - 并发 128：−27%（−11%）；
  - 并发 256：−7%。
- **影响**：
  - 图 6 的比例（发 kernel 占时间多少、同步占多少、graph 占多少）只用来看方向；
  - 数值大小以 B 段的 CUDA event 和打点为准。

## 3. CPU 各步的时间区间来自打点，不是 profiler

- **是什么**：torch profiler 只录启动它的那个线程的 record_function 范围。code2wav 的计算在调度线程上，所以 trace 里没有我们加的 c2w.* 范围。
- **做法**：用打点事件里的 CPU 时间区间（墙钟），去对 trace 里的 CUDA 调用和 kernel。
- **对齐检查**：3 个区组共 182 批，打点事件的“拷回结束”比 trace 里对应拷贝调用的结束晚，中位数 39 微秒，范围 22–86 微秒（results/clock_alignment.json）。对齐误差远小于各段的毫秒级时间。

## 4. GPU 时间是“跨度”，不是独占计算时间

- **是什么**：flow、HiFT 的 GPU 时间是同一条 stream 上两个 CUDA event 之间的时间。同卡的 talker 也在跑，这段时间里 GPU 会轮流去执行 talker 的 kernel。
- **影响**：
  - “每个请求约 150 毫秒 flow GPU 时间”是在和 talker 共用卡的情况下测的；
  - 低负载（并发 8）时更接近独占时间：每帧 104 微秒，高负载时是 157–169 微秒；
  - 独占时间要看实验 7 里 code2wav 单独占卡的放置。

## 5. “逐个发 kernel 慢多少”是按帧数折算的

- **是什么**：走 graph 的请求都 ≤ 1024 帧，逐个发 kernel 的都 > 1024 帧，两组长度不同。我们按“时间和帧数成正比”折算到每帧再比较。
- **影响**：flow 有注意力层，计算量随帧数增长得比线性快，所以折算后的差别（并发 8 时 16%）里，可能有一部分是长请求本身更贵。
- **这条曾经出过错**：报告初稿直接比较了 88 和 133 毫秒，写成“多 50%”，并据此把 H2 判为“支持”。按帧数折算并对照事先的判定标准后，已改正为“高负载下不支持”。

## 6. HiFT 开头的同步：现象是实测，原因是推断

- **实测**：trace 里每批的 HiFT 区间有 2–4 次 cudaStreamSynchronize，第一次一直等到 flow 在 GPU 上算完。
- **推断**：来源是 decode_waveforms 里用 Python 列表索引（mel[row_indices, ...]）时，PyTorch 做的同步拷贝。我们没有改代码去验证。

## 7. 批大小不是我们控制的

- 批大小由负载自己决定：高负载时批大，同时争用也重。
- 图 5 的“凑批不省时间”是相关关系。在同一并发档内比较也没有下降（并发 128 时等级相关 +0.06，并发 256 时 +0.40），但没有做“固定负载、只改批大小上限”的干预实验。

## 8. 只有 3 个区组

- 95% 区间用自由度 2 的 t 值（4.303），所以很宽。
- 结论主要看 3 个区组的方向是否一致和效应大小，不声称统计显著。

## 9. 过程上的偏离

- **测量补丁先写、检查后补**：sglang-omni 的测量补丁是先写好的，CPU 检查（configs/runtime/patches/check_sglang_omni_instr.py）是后补的。
  - 补救做法：在没打补丁的副本上运行检查，确认它失败（SimpleScheduler 没有 trace_part）；在打补丁的副本上运行，确认它通过。
  - 这不是严格的“先写测试”。
- **分析脚本的测试**：tests/test_exp06_c2w_breakdown.py 的大部分测试和脚本是一起写的。
  - 两处是先改测试、再改代码：kernel 排队延迟只算每次发 kernel 的第一个 kernel；用打点的 CPU 区间做归属。
  - 测试里有一处预期值曾经手算错（graph 占比 30/160，应为 30/170），已改正。
- **nsys 和 ncu 没有用**：节点上有 nsys 2024.6.2 和 ncu 2025.1.1，但没有测试它们和 CUDA 13 运行时是否兼容。kernel 级的数据全部来自 torch profiler。

## 10. 适用范围

- 只测了一种负载：W3b（文字提问、最多 64 个文字 token、语音 8–17 秒）。只测了一种放置：2+6，code2wav 和 talker 同卡。
- 换成更长的回答、音频输入，或其他放置，各段的比例会不同，比如 flow 帧数更多时，走 graph 的比例更低。
- 只在一台节点（compute-03）、一个 Slurm Job（454290）上测。
