# 实验 6 的假设与判定标准（预先登记）

> 写于 2026-11-17 14:30（美东），在实验 6 的任何正式数据产生之前。之后如果改动分析方法，会在 `limitations.md` 里写明改了什么、为什么改，原来的方法也照样报告。

## 研究问题

实验 5 看到：2+6 分工下，code2wav 阶段（从派发到完成）的中位数在并发 8 时约 0.16 秒，并发 256 时约 5.56 秒。这段时间里包括排队、凑批、CPU 准备、发 kernel、GPU 计算、同步等待、后处理。本实验要把它拆开，回答它为什么变长了 30 多倍。

## 从源码已经知道的事（sglang-omni 520b49ee，均为实测阅读）

- code2wav 的调度器是 `SimpleScheduler`（`sglang_omni/scheduling/simple_scheduler.py`）：一个线程，串行处理。
  - 每次从收件队列取一个请求。
  - 在 `max_batch_wait_ms` 内再取几个，凑成一批。
  - 一批算完才取下一批。
- 现有的 `stage_dispatch` 事件在请求放进收件队列之前发出（`sglang_omni/pipeline/stage/runtime.py` 第 1115 行附近）。所以“派发→完成”包含排队。
- 一批的计算是 `vocode_code2wav_payloads` → `MiniCPMOCode2Wav.vocode` → `decode_waveforms`（`sglang_omni/models/minicpm_o/components/code2wav.py`），依次做四件事：
  1. 准备说话人参考；
  2. flow 对整批一起算 10 步，补齐到最长的请求；
  3. HiFT 按编码长度分组，每组单独算；
  4. 最后用 `.cpu()` 把波形拷回 CPU，这是这一批唯一的自然同步点。
- flow 只有在录过的形状里找到“同样 batch 大小、帧数不小于当前这批”的 CUDA graph 时才走 graph，否则逐个发 kernel（`flow_cuda_graph.py` 的 `fit`，未命中时 `graph_misses += 1`）。

## 实验单位和设计

- **实验单位**：一次独立启动的服务（2+6 分工，8 张 A6000）。同一次运行里的请求互相影响（闭环、凑批），不算独立重复。
- **重复**：3 次独立运行（区组 1–3），按时间先后跑在同一台节点上。
- **处理因素**：
  - 并发 8、64、128、256。每个区组内的顺序随机，种子 20261117，顺序表写在配置里。
  - 测量方式三种：A 不打点、不开 profiler；B 打点；C 打点并在中间开几秒 torch profiler。每个并发档内 A、B、C 的顺序按区组轮换（ABC、BCA、CAB），用来平衡先后顺序的影响。
- **每个并发档**：先跑一波预热（并发数个请求，不计入），然后 A、B、C 各测 max(96, 3×并发) 个请求。
- **另外两项单独做**：
  - 一次 nsys 时间线：并发 128，几秒；
  - 一次 ncu 微观测量：只测热点 kernel，在服务之外单独跑。
  - 两者都不参与吞吐和延迟的比较。

## 主要指标（每个请求，再汇总到每次运行）

| 指标 | 定义 | 来源 |
|---|---|---|
| 阶段墙钟时间 | 派发 → 完成 | 现有事件 |
| 排队等待 | 进收件队列 → 被调度线程取出 | 新增事件 |
| 凑批等待 | 被取出 → 这一批凑齐 | 新增事件 |
| 计算墙钟时间 | 这一批开始计算 → 算完（同一批的请求共享） | 新增事件 |
| CPU 各段 | 准备参考、发出 flow、发出 HiFT、等拷回（同步）、后处理 | 新增事件，同一线程上依次发生，可以相加 |
| GPU 各段 | flow、HiFT 在 code2wav 那条 stream 上的时间跨度 | CUDA event，和 CPU 各段时间上重叠，不能和它们相加 |
| 每批信息 | batch 大小、编码 token 总数、最长帧数、HiFT 分组数、flow 走 graph / 打包 graph / 逐个发 kernel | 新增事件 |
| 发 kernel 的 CPU 时间、设备排队延迟、kernel 执行时间、同步等待 | 短窗口 kernel trace 里 code2wav 进程的 CUDA 调用与 kernel 的对应 | torch profiler |

一批 GPU 时间只算一次，不按请求重复累加。

## 假设与判定

### H1：高负载时 code2wav 变慢，主要是因为在收件队列里排队

- **看什么**：并发 8 → 256，阶段墙钟时间的中位数增量里，排队等待的中位数增量占多少。
- **支持**：占一半以上，而且每批的计算墙钟时间增长不到 2 倍。
- **反驳**：计算墙钟时间的增量占一半以上。
- **数据不足**：如果新增事件丢失或时间顺序矛盾，导致排队等待算不出来，就标“未知”，不用“阶段时间 − 计算时间”的差去冒充排队时间。

### H2：code2wav 有明显的 CPU 发 kernel 开销

- **看什么**：
  - 每批里，CPU 在 CUDA 发 kernel 调用（`cudaLaunchKernel`、`cuLaunchKernel` 等）上花的时间占计算墙钟时间的比例；
  - code2wav 这条 stream 在计算期间没有 kernel 在跑的比例；
  - flow 的“CPU 发出时间”和“GPU 时间跨度”之比。
- **支持**：发 kernel 的时间占计算墙钟时间 30% 以上，而且 GPU 跨度和 CPU 发出时间接近（GPU 在等 CPU）。
- **反驳**：CPU 很早就发完了，GPU 跨度明显长于 CPU 发出时间，code2wav 的 kernel 之间几乎没有空隙。
- **注意**：profiler 会放大发 kernel 的开销。所以比例只用来定方向，大小以“CPU 发出时间 / GPU 跨度”（来自打点，不开 profiler）为准。

### H3：真正的瓶颈是 GPU 计算，或者和 talker 抢 GPU

- **看什么**：
  - 同样形状的 batch，flow、HiFT 的 GPU 跨度随负载怎么变；
  - kernel trace 里 talker 和 code2wav 的 kernel 同时在跑的比例；
  - talker 卡总的忙碌比例。
- **支持**：
  - 高负载时卡几乎一直在算（≥ 90%），同形状 batch 的 GPU 跨度随负载变长（被 talker 挤占）；
  - 或者 code2wav 本身的 GPU 计算量就超过了它在这张卡上能分到的时间。
- **反驳**：高负载时卡上还有明显空闲（≥ 20%），请求却在排队。那瓶颈在 CPU 或串行调度，不在 GPU。
- **因果检验**：只靠本实验无法证明。要看实验 7 把 code2wav 搬走以后，同形状 batch 的 GPU 跨度会不会变短。

### H4：凑批会改变每个请求的等待时间和每秒语音的计算成本

- **看什么**：
  - 每批计算墙钟时间与 batch 大小、HiFT 分组数的关系；
  - flow 和 HiFT 各自“每秒语音的 GPU 时间”随 batch 大小怎么变。
- **支持**：flow 每秒语音的成本随 batch 变大而下降，HiFT 基本不降（它按长度分组，长度不同就各算各的）。
- **反驳**：两者都随 batch 明显下降，或者都不下降。
- **注意**：batch 大小不是我们控制的，而是由负载决定，和并发高度相关。所以这一条只能报告相关关系，不能当作因果。

## 统计分析（预先确定）

- **单位**：每次运行先算出各指标的中位数、P95、P99（请求级），然后以运行为单位汇总。报告 3 次运行的原始值、均值，以及基于 t 分布的 95% 置信区间（自由度 2，区间会很宽，不做显著性声明）。
- **开销**：同一区组内，B 相对 A、C 相对 A 的吞吐与中位数延迟的相对差，报告 3 个区组的原始值和均值。
- **排除规则**：
  - 预热请求不计；
  - 失败、超时的请求单独计数并报告，不参与延迟统计；
  - 如果某一档错误率超过 5%，这一档整体标为“不可用”，不删除。
- **不做的事**：不在看到结果之后换指标、换分位数或剔除“异常”运行；如果有运行因为崩溃等原因重跑，原来的运行也保留并报告。
