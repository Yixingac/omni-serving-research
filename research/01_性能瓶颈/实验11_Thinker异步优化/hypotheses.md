## 先说清楚“提前发射”是什么

- 它不是推测解码（speculative decoding）。GPU 不会去猜下一个 token。
- 它是调度上的重叠：CPU 先把第 N+1 步发给 GPU（第 N+1 步的输入 token 已经在 GPU 上，由第 N 步在 GPU 上采样得到），然后再回头处理第 N 步的结果（把 token 拷回 CPU、判断是否结束、整理输出）。
- 风险在于第 N+1 步重放 CUDA graph 时，会覆盖第 N 步的隐藏状态输出缓冲区，而 MiniCPM-o 要在处理第 N 步结果时才读它。实验 8 的原型在每步发射后立即把隐藏状态复制一份（快照），解决了这个问题。

## 源码审查（sglang-omni 520b49ee + 实验 8 原型）

1. **请求结束时的阻塞拷贝**：`MiniCPMOThinkerModelRunner.on_request_finished` 用 `torch.stack(seq).to("cpu")` 把这个请求累积的隐藏状态拷回 CPU。
   - 拷到普通（可分页）内存，CPU 要等这条流上排在它前面的所有工作完成；
   - 提前发射时，下一步已经排在前面，所以要多等约一步。
   - 这和实验 8 测到的 320–520 KB、22–24 毫秒的阻塞拷贝吻合，但当时没有调用栈，属于推断。
2. **逐行复制**：每步处理结果时，每个请求的那一行用 `clone()` 复制。这个复制排在当前流上，也就是排在下一步后面，所以“这一行什么时候可用”同样晚一步，只是不阻塞 CPU。
3. **TTFT**：调度循环先发第 N+1 步，再等第 N 步。新请求大多在 CPU 等第 N 步时到达；下一轮发现它时，第 N+1 步已经在 GPU 上排队，必须先等它算完（代码里的 mixed_chunk flush），才能做新请求的 prefill。同步执行时只需等正在算的那一步。
   - 推断：多出来的约等于一个 decode 步。这是“只对纯 decode 提前发射、混合轮次同步执行”这个设计本身的代价，已经发给 GPU 的那一步撤不回来。
   - 本实验不尝试修复它，只用新数据确认机制。

## 原型（configs/runtime/patches/sglang_omni_async_exp11.patch）

在实验 8 的原型之上新增模式 `SGLANG_OMNI_SPEECH_LOOKAHEAD=sidecopy`：
- 和模式 1 一样做快照；快照之后立即在发射用的流上记一个 CUDA 事件。
- 处理第 N 步结果时，在**另一条流**（旁路流）上先等这个事件，再做逐行复制。
  - 这条流不等第 N+1 步；
  - 用 `record_stream` 告诉显存分配器：快照的显存要等旁路流读完才能复用；
  - 事件和快照张量一起保存，查找时核对是不是同一个张量对象，避免地址复用造成错配。
- 同步执行的步（prefill、混合轮次）照旧在发射流上复制，并记一个事件。
- 请求结束时，旁路流先等这个请求最后一个“发射流上的行”，再在旁路流上合并、拷回 CPU。
  - CPU 仍然等这次拷贝本身（几百 KB，预计约 0.1 毫秒），但不再等下一步。
- 所有模式都在“请求结束时的拷贝”外面加了 profiler 标注 `thinker.request_finished_copy`，在调度循环的每次发射外面加了 `thinker.step<序号>.<模式>.<la|sync>` 标注。这样 torch trace 能把 GPU kernel 对应回调度器的逻辑步，包括不走 CUDA graph 的步。
- 打开 digest 时，每个请求还记下隐藏状态每一行的 L2 范数和在 4 个固定随机方向上的投影（指纹），用来在哈希无法完全一致时按容差比较。
- **没有用固定内存（pinned memory）**：拷贝仍然是同步的，只是放在不等下一步的流上。额外的显存只有每步一份快照（批大小 × 4096 × 2 字节，最多约 0.5 MB），在这一步处理完后释放。
- CPU 检查 `configs/runtime/patches/check_sglang_omni_async.py`：用替身对象核对控制流程和数据；真正的并发正确性由下面的 GPU 正确性检查回答。

## 正确性检查（性能对比的前提）

- 三次独立启动：A、C、A2（A 的重复，用来估计同一种设置自己重复时的差别）。打开 digest。负载用贪心版本（thinker、talker 温度 0，seed null）。
- 段落：
  1. 并发 1，18 个请求，逐个请求比较文字、隐藏状态哈希、语音编码哈希（同实验 8）；
  2. 并发 8、32、64，分别 48、96、128 个请求；
  3. 并发 32 的混合负载：
     - 文字和文字 + 语音各一半；
     - 短回答和长回答各一半；
     - 带 seed 0（不能提前发射）和 seed null 各一半，同一批里有的能提前、有的不能；
  4. 客户端 1.5 秒就放弃的长回答，并发 32，64 个请求（服务端中途中止请求）；
  5. 紧接着一段普通的并发 32、96 个请求，检查中止之后服务是否干净；
  6. W3XL 并发 8、32 个请求，核对实际输出长度（有没有达到 talker 上限）。
- **判定（全部满足才通过）**：
  - 并发 1：C 对 A，18 个请求的三样东西逐个相同；
  - 所有段（第 4 段的超时除外）没有报错；每个完成的语音请求，隐藏状态的行数都等于它的文字 token 数；
  - 并发 8 以上和混合段：按请求序号配对、文字相同的请求之间比较指纹，记最大相对偏差。C 对 A 中偏差 > 0.05 的请求比例，不比 A2 对 A 的比例高出 5 个百分点以上；
  - 第 5 段 0 错误。
- 任何一条不满足，或者出现无法解释的跨请求数据污染，就**不做 C 的性能对比**，只报告失败证据。

## 性能对比

- 3 个区组，每个区组 A、B、C 各一次运行。组的先后按拉丁方：区组 1 是 A→B→C，区组 2 是 B→C→A，区组 3 是 C→A→B。
- 每次运行：
  - W3b（seed null）并发 8、32、64，顺序在每个区组随机（种子 20261118），三组共用；
  - 每档 A、B、C 三段，按区组轮换 ABC、BCA、CAB：
    - A 段不打点，看吞吐、延迟、TTFT、显存；
    - B 段开事件，看提前发射比例、混合轮次比例、每个 token 的时间、TTFT 拆分；
    - C 段只给 thinker 进程开 3 秒 torch profiler，看空档和阻塞调用；
  - 然后是长回答：W3L 和 W3XL（seed null）各在并发 32 做 A 段和 B 段。
- **空档的算法**：
  - 用调度步的标注把 GPU kernel 对应到逻辑步。每一步的“空档”是这一步第一个 kernel 开始，减去上一步最后一个 kernel 结束；
  - 不走 graph 的步单独标出；
  - 报告中位数、P95、P99，以及按时间加权的空档比例（所有空档之和 ÷ 窗口时长），也按步的类型分开报告。
  - 异常长的步要检查是计算变慢，还是中间漏了步。

## 假设与判定

所有比较都按区组配对，报告每个区组的值、均值和 t 分布 95% 区间（自由度 2）。

### H11a：TTFT 变长发生在新请求插入的路径上

- W3b 并发 8 和 32，B 对 A、C 对 A：
  - **支持**：TTFT 均值的增加里，“进入调度队列 → prefill 开始”这一段在 3 个区组都占 ≥ 80%；
  - **反驳**：这一段在 3 个区组都占 < 50%；
  - 其余**不确定**。
- 另外报告：多出的排队时间和一个 decode 步的 GPU 时间之比。

### H11b：请求结束时的阻塞拷贝来自 on_request_finished

- B 组的 C 段 trace 里，大于 1 KB、阻塞超过 1 毫秒的拷贝：
  - **支持**：在 3 个区组都有 ≥ 90% 落在 `thinker.request_finished_copy` 标注之内；
  - **反驳**：都 < 50%；
  - 其余**不确定**。

### H11c：旁路复制减少剩下的 GPU 空档

- C 对 B，W3b 并发 32 和 64：
  - **支持**：每步的大块阻塞拷贝在 3 个区组都减少 ≥ 90%，并且并发 64 时按时间加权的空档比例在 3 个区组都下降 ≥ 2 个百分点；
  - **不支持**：空档比例在 3 个区组都没有下降；
  - 其余**不确定**。

### H11d：这些变化能转化成端到端的改善

- C 对 B、C 对 A，W3b 并发 32 和 64，端到端 P50：
  - **支持**：在 3 个区组都下降 ≥ 2%；
  - **不支持**：在 3 个区组都没有下降；
  - 其余**不确定**。
- 吞吐、P95、P99、TTFT 同样报告。

### H11e：回答越长，提前发射的收益越大

- 并发 32，C 对 A：
  - **支持**：每个请求在 thinker 里省下的总时间（每个 token 省下的时间 × token 数）在 W3XL 和 W3L 上都大于 W3b，并且端到端 P50 的相对改善在 W3XL 上大于 W3b，都在 3 个区组成立；
  - **不支持**：端到端的相对改善在 W3XL 上在 3 个区组都不大于 W3b；
  - 其余**不确定**。
