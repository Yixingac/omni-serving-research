# 当前系统和已有实验说明

本文回答一个问题：**MiniCPM-o 4.5 在这 8 张 GPU 上到底是怎么运行的？** 然后列出已经做了哪些实验、还缺哪些数据。

所有说法都按仓库里的代码、配置和实测数据核对过。代码版本：本仓库分支 `research/agent-trace-end-to-end`，sglang-omni `520b49ee`，sglang 0.5.21，torch 2.13.0。

## 1. 一个请求是怎么走完的

### 1.1 进入系统

1. 客户端（我们的压测程序）向服务发一个 HTTP 请求。接口和 OpenAI 的 `/v1/chat/completions` 一样，内容是一段对话；要语音回答的请求还会写明输出包含 audio。
2. 服务里的 **coordinator**（协调进程）收下请求，交给第一个阶段。它不用 GPU。
3. **预处理**：把文字变成 token（模型能读的数字编号），拼成模型的输入。它也不用 GPU。

### 1.2 三个主要阶段

| 阶段 | 是什么 | 做什么 | 计算特点 |
|---|---|---|---|
| Thinker | 8B 规模的语言模型，结构同 Qwen3-8B（36 层，hidden 4096） | 读问题，一个 token 一个 token 地写出文字回答，同时把文字流式发回给用户 | 每写一个 token 都要从显存读一遍约 15 GB 的权重，速度主要受显存带宽限制 |
| Talker | 小得多的模型，约 0.2B 参数 | 把 thinker 写好的回答变成“语音 token”，也就是声音的压缩编码 | 也是一个 token 一个 token 地生成 |
| Code2Wav | 声码器（flow 模型 + HiFT 网络） | 把语音 token 还原成 24 kHz 的声音波形 | 计算量大，受算力限制 |

**两个概念：prefill 和 decode**

- **Prefill（读入提示）**：模型第一次看到问题时，把所有输入 token 一次性算完。W3b 的问题只有约 26 个 token，所以 prefill 很快，约 30 毫秒。
- **Decode（逐个生成）**：之后每一步只生成一个新 token，下一步要用上一步的结果，所以只能一步一步来。W3b 的回答约 45 个 token，thinker 就要走约 45 步，每步约 26 毫秒，合计约 1.2 秒。
- 代码里还有一个叫 decode 的阶段，负责把 token 变回文字、流式发给用户。它不用 GPU，和这里说的“逐个生成”不是一回事。

### 1.3 三段是串行的

```text
用户 ─► coordinator ─► 预处理 ─► Thinker ───────► Talker ──────► Code2Wav ─► coordinator ─► 用户
                                 （写完整个回答）   （做完所有语音 token）
                                 文字边写边发给用户
```

- 在当前代码里，MiniCPM-o 要等 thinker 写完整个回答，talker 才开始；talker 做完，code2wav 才开始。
- 所以语音是在最后一次性返回的。用户等到第一段声音的时间，约等于整个请求的时间（实验 1：并发 8 时约 2 秒）。

### 1.4 为什么要分成多个阶段

- 三个模型的计算特点完全不同：thinker 受显存带宽限制，code2wav 受算力限制，talker 很小。
- 分开以后，每个阶段可以单独决定放在哪张卡上、复制几份。负载大的阶段多给几张卡，负载小的少给。
- 代价：阶段之间要传数据，一个请求要依次走完所有阶段，中间任何一段慢了都会拖住整个请求。

## 2. GPU 怎么分工

### 2.1 几个说法

- **完整副本（full replica）**：一张卡上放全部阶段，自己就能完整处理一个请求。8 张卡就是 8 个互不相干的服务，客户端把新请求交给手上请求最少的那个。
- **流水线（pipeline）**：不同阶段放在不同的卡上，请求像工厂流水线一样，从一张卡流到下一张卡。
- **阶段复制（stage replication）**：同一个阶段复制多份，分别放在几张卡上，一起分担这个阶段的工作。

### 2.2 为什么要把阶段放到不同的卡上

- 放在同一张卡上时，三个进程轮流使用 GPU，互相拖慢。实验 1 里，8 个完整副本在高负载时，thinker 每 token 从 26 毫秒变成 81 毫秒。
- 放在不同的卡上，每个阶段独占 GPU，但要算好每个阶段给几张卡：给少了，这个阶段排队；给多了，卡闲着。

### 2.3 已经比较过的 8 卡分工

所有分工里，code2wav 都是单独的进程，和 talker 放在同一张卡上。原因是 talker 和 code2wav 在同一进程里并发运行会崩溃，见实验 18（原实验 10）。

```text
方案 A：8 个完整副本（内部代号 R8）
  GPU0 [T+K+C]  GPU1 [T+K+C]  GPU2 [T+K+C]  GPU3 [T+K+C]
  GPU4 [T+K+C]  GPU5 [T+K+C]  GPU6 [T+K+C]  GPU7 [T+K+C]
  T = thinker，K = talker，C = code2wav

方案 B：4 条两卡流水线（P4）
  GPU0 [T] ─► GPU1 [K+C]
  GPU2 [T] ─► GPU3 [K+C]
  GPU4 [T] ─► GPU5 [K+C]
  GPU6 [T] ─► GPU7 [K+C]

方案 C：一个服务，2 张 thinker 卡 + 6 张 talker 卡（S2:6）
  GPU0 [T]  GPU1 [T]
      │  thinker 写完的回答，交给下面 6 张卡中的一张
      ▼
  GPU2 [K+C]  GPU3 [K+C]  GPU4 [K+C]  GPU5 [K+C]  GPU6 [K+C]  GPU7 [K+C]

方案 C 的变体：thinker 卡数从 1 到 6（S1:7、S3:5、S4:4、S5:3、S6:2），其余的卡都给 talker+code2wav。
```

### 2.4 为什么要比较不同的分工

- 每个阶段要多少算力，取决于负载：回答长不长、有没有语音、同时有多少请求。
- 没有一种分工在所有情况下都最好。实验 1、2 已经看到：
  - 低负载时各种分工差不多；
  - 高负载时，talker 卡多的分工（2+6、1+7）在同样速率下能扛住更多请求。
- 比较分工，就是在问：“在什么负载下，8 张卡怎么分最划算？”

## 5. 现在缺什么数据

| 缺口 | 影响 | 计划 |
|---|---|---|
| GPU kernel 级时间线 | 原来看不到每一毫秒 GPU 在跑什么 | **已补上**：实验 1 在 compute-03 上录到了三种分工的 kernel 时间线（并发 8、64）。还缺：稳定满负载下的长窗口，以及 Python 调用栈 |
| code2wav 内部的排队和计算分不开 | 高负载时最大的等待点，说不清是在排队还是在算 | **已补上**：实验 6 用打点补丁把 code2wav 的排队、凑批和 GPU 计算拆开了（并发 256 时 42% 排队、58% 等同批一起算完） |
| 每一步实际的 batch 大小 | 只能用 Little 定律推算平均值 | **部分补上**：实验 4 用平均值（有效 batch）和服务日志里 code2wav 每一批的请求数，回答了“batch 变大是更快还是更慢”。thinker 和 talker 每一步的 batch 仍然没有：SGLang 日志里有每步的在跑请求数，但两者写在同一个日志里分不开，可以让各进程分别写日志 |
| CPU 端每一步具体在做什么 | 实验 1 测到 thinker 每一步有 3–5 毫秒在等 CPU，talker 手上有活时约四成时间空着，但不知道 CPU 具体在忙什么 | **部分补上**：实验 5 第二版从 trace 里的 CUDA 调用看出，thinker 每一步先同步等 GPU 算完，再花 2–5 毫秒准备下一步（语音请求关掉了提前一步发射）；talker 用上了提前一步发射，每步几乎不空。还缺：这 2–5 毫秒里 Python 具体在做什么，要开调用栈记录 |
| 重复次数 | 实验 1 的主要结论有 2–3 次重复，实验 6–11 按 3 个区组设计；实验 3、4、12、13、14、19 用的配置都只跑了 1 次 | 关键结论补到 3 次（各实验 README 第九部分列了先补哪几个） |
| Nsight Systems | 没有更细的工具 | torch profiler 在 compute-03 上能录到 kernel，暂时够用；确实需要再申请安装 |
