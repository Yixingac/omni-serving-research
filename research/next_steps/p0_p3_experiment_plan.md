## P0：talker 的并发上限是不是 2+1+5 的瓶颈

### 先用 8 个问题说清楚

| 问题 | 回答 |
|---|---|
| 1. 想解决什么 | 只给 talker 1 张卡（2+1+5）时，它的卡只忙 65% 却成了瓶颈。想知道卡住它的是“最多同时处理 32 个请求”这个软件上限，还是 GPU、显存或 CPU |
| 2. 为什么认为有问题 | 软件上限和 GPU 忙碌比例对不上：GPU 有 35% 空着，请求却在 talker 前排队 8 秒 |
| 3. 哪个实验发现的 | 实验 9（方案 3）；本轮从实验 9 的调度日志补了直接证据（下表） |
| 4. 别人怎么做 | SGLang 的调度器按 `max_running_requests` 和 KV 余量准入；ThunderAgent 等系统按“程序”而不是请求做准入（相关工作文档）。没有找到针对 omni talker 的准入研究 |
| 5. 怎么验证 | 2+1+5 上只把 talker 名额从 32 改到 64，3 个区组配对；同时用日志核对名额、KV、CUDA graph 和每步时间 |
| 6. 可能有多少收益 | talker 吞吐 +10% 到 +20%（Estimated，按实测的“批大小—每步时间”曲线外推），**多半追不上 2+2+4** |
| 7. 结果不好能学到什么 | 如果名额放开后吞吐不涨，就说明瓶颈是 talker 每步的 GPU/CPU 时间本身，下一步应该优化 talker 的每步开销（见 compiler 文档的 talker 部分），而不是调参数 |
| 8. 值得继续吗 | 值得，成本最低（只改一个配置）、信息量大；它决定“1 张 talker 卡够不够”，直接影响 3+1+4 这类新分法 |

### 已有证据

| 事实 | 等级 | 来源 |
|---|---|---|
| talker 名额默认 32，代码写死在 MiniCPM-o 的 talker 构造里 | 源码 | `sglang_omni/models/minicpm_o/stages.py:143-144`（`max_running_requests=32`）；thinker 是 64（同文件 `:361`） |

| talker 的 KV 上限默认 `32 × 4096 = 131072` token，与名额无关（`setdefault`），注释写“不让 talker 饿死 thinker” | 源码 + Measured | `stages.py:160-161`；启动日志 `KV Cache is allocated ... #tokens: 131072, K size: 3.75 GB, V size: 3.75 GB`，可用于 KV 的显存 18.13 GiB |
| 2+1+5、W3b 并发 256：唯一 talker 的 decode 日志行 80–83% 正好 32 个在跑、同时排队 178–184 个；W3L 并发 128：81–84%，排队 53–58 | Measured（启发式区分 talker 行，见脚本说明） | `results/p0_k1c5_talker_slots.json`、`results/p0_k1c5_w3l_talker_slots.json`（`scripts/analysis/next_talker_slots.py`） |

| 独占卡 talker 的每步时间：批 16 → 24 → 32 为 2.62 → 3.30 → 4.01 ms；吞吐 6111 → 7272 → 7982 token/s | Measured（SGLang 日志的 gen throughput，3 个区组合并） | `results/p0_k1c5_talker_slots.json` 的 `decode_curve_all_lines` |
| 独占卡 talker（2+2+4，并发 128，profiler 窗口）：每步约 180 个 kernel，中位 1.9 µs，96–97% 来自 CUDA graph，卡只忙 52–60% | Measured（只在 profiler 窗口里，CPU 侧被放慢） | 实验 7 `t2_k2_c4_block1` 的 talker trace（集群，不公开） |

**由此推出的事先预测（Estimated，登记于 2026-11-18）**：
- 每步时间在 16–32 之间近似线性增长，斜率约 0.088 ms/请求。按这个斜率外推，批 64 时每步约 6.8 ms，吞吐约 9.4k token/s，比批 32 多约 17%。
- 预测区间：talker 吞吐 +10% 到 +20%；2+1+5 的 W3b 登记容量从 17.75 到约 19.5–21.3 请求/秒，**仍低于 2+2+4 的 23.77**。
- KV 不会先满：talker 每 token 的 KV 是 60 KiB（20 层 × 12 个 KV 头 × head_dim 64 × K/V × BF16），131072 token 的池约 7.5 GiB（启动日志 K、V 各 3.75 GB，Measured；`docs/04_experiments/plan_8gpu_v2.md` 等处写的“约 15 GB”是按显存比例算的预算，不是实际的池）。W3b 的 talker 请求约 450 token、W3L 约 900 token（隐藏状态行 + 每秒 25 个语音编码），64 个请求实际占用最多约 58k token（Derived）。但 SGLang 准入时要为新请求留出 输入 + min(2048, 4096) token 的余量，并为每个在跑请求预留“剩余可生成 token × new_token_ratio”（比例从 0.7 衰减到约 0.1；`python/sglang/srt/managers/schedule_policy.py:788-796, 1347-1366`），按 0.7 估算 64 个 W3b 请求约预留 105k token，仍在 131072 以内（Estimated）。所以必须在日志里核对 `token usage` 和“在跑 < 64 却排队”的行。

### 判定（事先写定）

- **H0a（名额是限制）**：B 的 W3b 登记容量在 3 个区组都比 A 高 ≥ 5%，并且 B 的高负载档里 talker 在跑中位数 > 32。→ 支持；3 个区组都 < 2% → 反驳；其余不确定。
- **H0b（放开后瓶颈是什么）**，只在 H0a 支持或不确定时判：
  - B 里 talker 仍是驻留量最大的阶段，且 talker 进程 CPU ≥ 95% 单核、GPU 忙 < 80% → “CPU/调度受限”；
  - talker 卡 GPU 忙 ≥ 90% → “GPU 受限”；
  - 方案 C 触发 → “KV 预留受限”；
  - code2wav 成为驻留量最大的阶段 → “瓶颈转移到 code2wav”。
- **H0c（能否追上 2+2+4）**：B 对参照 t2_k2_c4 的配对差，3 个区组都 ≥ 0 → 支持；都 < 0 → 反驳。登记的预测是“反驳”。
- 排除规则沿用实验 9（错误 + 超时 > 5% 的档不进判定，服务重启的段标缺失，不删运行目录）。

### 可能失败的原因

- 每步时间在 32 以上变陡（attention 随 KV 变长、sampling 是逐行的），收益接近 0；
- talker 的 CPU 循环（每步约 180 个 kernel 的 graph 重放之间的 Python 工作）在批更大时更慢，GPU 空档不减反增；
- 名额放开后 KV 预留触发 retract（日志会有 retract 记录），反而抖动。
这几种都能从日志直接区分，所以“失败”也给出下一步方向。

## P1：按长度组批 + 最长等待，在完整服务上有没有用

### 8 个问题

| 问题 | 回答 |
|---|---|
| 1. 想解决什么 | 实验 10 的按长度组批只在 code2wav 排长队时有用（+30%），完整服务没饱和时没有差别，而且一部分短请求等得更久。想知道：服务接近或超过饱和时它能否推高稳定容量，加上“最长等待”能否消掉短请求的长尾 |
| 2. 为什么认为有问题 | 长短混合时先进先出按最长的补齐，28% 的计算白算（实验 10，Measured） |
| 3. 哪个实验发现的 | 实验 6（自然凑批不省）、实验 10（主动按长度组批 +30%，验证不确定） |
| 4. 别人怎么做 | 上游 issue #1236 发现 code2wav 凑批的收益取决于请求是否对齐到达；VoxServe 按 TTFA/卡顿 SLO 调度语音流；OmniCast 按播放进度和首音频优先级调度（`docs/01_research/prior_work.md` 4.3）。“按长度分桶 + 老化（aging）”本身是常见的调度手段，不是新方法 |
| 5. 怎么验证 | 2+2+4 上把开环速率推过饱和点，短、长、混合三种负载分开，FIFO16、Length8、Length8 + 最长等待（3 个阈值）在同一运行里用控制文件切换，3 个区组 |
| 6. 可能有多少收益 | 只在饱和区：code2wav 每秒语音最多 +11%（W3b）到 +30%（MIX）（实验 10 在 code2wav 饱和时测到的上限）。完整服务的稳定容量收益会更小，因为 2+2+4 在 W3b 上接近 code2wav 与 talker/thinker 能力相等的点（Estimated） |
| 7. 结果不好能学到什么 | 如果饱和区也没有收益，说明 2+2+4 的 code2wav 在饱和前已不是唯一瓶颈，按长度组批只适合 code2wav 卡少的放置；这本身就是“局部优化不转化为端到端”的一个定量例子 |
| 8. 值得继续吗 | 值得做一次。改动小（只改出队顺序），但要先把“最长等待”实现并通过 CPU 检查 |

### 最长等待的设计和阈值依据

- **算法**（在实验 10 的 `collect_length_aware` 上改）：取批时先找出窗口里等待时间 ≥ τ 的请求，按到达顺序放进批（不超过批上限）；剩下的名额再按“和最老请求的长度最接近”挑。没被挑上的请求照旧按到达顺序放回队首。τ = ∞ 就是 Length8，τ = 0 退化为 FIFO8。
- **需要的改动**：入队时记下单调时钟（`SimpleScheduler` 收到消息时），控制文件多一个键 `max_wait_ms`；每批的事件里记下“因超时被强制放入”的请求数。CPU 检查仿照 `configs/runtime/patches/check_sglang_omni_batch.py`：构造到达时间和长度，检查超时请求一定被选入、批大小不超上限、顺序稳定。
- **阈值怎么定（依据，不是拍脑袋）**：
  1. **SLO 推出的排队预算**：本项目 SLO 是“端到端 ÷ 语音秒 ≤ 0.5”。W3b 最短的回答约 6 秒语音，总预算 3 秒；上游 thinker 约 1.2 s、talker 约 0.7 s、code2wav 计算约 0.2 s（实验 6、9 的中位数，Measured），留给 code2wav 排队的约 0.9 s。所以 **τ = 1 s 是主值**。
  2. **批服务时间**：length8 在 MIX 上每秒语音 8.5 ms GPU（实验 10），一批 8 个 MIX 请求（平均约 20 秒语音）约 1.4 s。τ 取 {0.5, 1, 2} s 就是“最多被跳过约半批、一批、两批”。
  3. 敏感度：τ ∈ {0.5, 1, 2} s，另有两个端点 Length8（τ = ∞）和 FIFO16（默认）。主判定只用 τ = 1 s，其余是敏感度，不改判定。

| 指标 | 来源 |

### 判定（事先写定）

- **H1a（饱和区有收益）**：MIX 1.0X、1.1X 两档，Length8+τ1 的 goodput 在 3 个区组都比 FIFO16 高 ≥ 5% → 支持；都 ≤ 0 → 反驳。
- **H1b（最长等待消掉长尾）**：MIX 上短请求排队 P99，Length8+τ1 在 3 个区组都比 Length8 低 ≥ 20%，且语音秒/秒不低于 Length8 的 95% → 支持。
- **H1c（短回答负载上不变差）**：W3b 上 Length8+τ1 的端到端 P95 不比 FIFO16 高 5% 以上（3 个区组）→ 支持。
- 不满足条件的写“不确定”，不做事后挑选。

### 可能失败的原因

- 2+2+4 在 code2wav 饱和前 talker 或 thinker 先满，组批方式没有可调的空间；
- 开环到达下队列在饱和区快速变长，任何出队顺序都只是在分配排队时间；
- 最长等待太小就退化成 FIFO，太大就保不住短请求——这正是敏感度要回答的。

## P2：隐藏状态异步拷贝的逐位正确性

### 8 个问题

| 问题 | 回答 |
|---|---|
| 1. 想解决什么 | 实验 11 的旁路复制没有通过正确性检查。要一个能逐位判断对错的检查，而不是靠容差和小样本 |
| 2. 为什么认为有问题 | 指纹检查每段只有 8–39 对请求，没有代码差别的两次运行之间比例也差 25 个百分点；它分不出小错误和抽样波动 |
| 3. 哪个实验发现的 | 实验 11（正确性未通过）、实验 8（不做快照时隐藏状态全错但不报错——这类错误是“静默”的） |
| 4. 别人怎么做 | 常见做法是“影子执行”（shadow execution）：同一份输入同时走参考路径和优化路径，逐位比对。这是工程实践，不是新方法 |
| 5. 怎么验证 | 同一次运行里，每个结束的请求同时保留“同步拷贝”和“旁路复制”两份隐藏状态，CPU 上 `torch.equal` 逐位比较，再核对行数与 token 数、行与 token 的对应 |
| 6. 可能有多少收益 | 正确性本身没有性能收益。即使通过，按实验 8 的数据，去掉阻塞拷贝对语音端到端的上限大约是 −2..−5% 再多一点（Estimated） |
| 7. 结果不好能学到什么 | 只要有一次不相等，就能定位到具体请求、具体行和当时的并发状态，比“比例超标”有用得多 |
| 8. 值得继续吗 | 值得做检查本身（成本低、可复用）；性能对比排在 P0、P1 之后 |

### 设计

- **改动**（在 `configs/runtime/patches/sglang_omni_async_exp11.patch` 上加一个模式 `SGLANG_OMNI_SPEECH_LOOKAHEAD=sidecopy_verify`）：
  1. 请求结束时，旁路流上的拷贝照常做（结果 R_side）；
  2. 同时在主流上等这个请求最后一个快照的事件，再用同步方式从同一批快照拷一份（结果 R_sync）；
  3. 两份都到 CPU 后：`torch.equal(R_side, R_sync)`、行数 = 文字 token 数、每行的 token 位置与 thinker 输出对齐（记录每行对应的 token id）；
  4. 不相等时记下请求 id、第一处不同的行、两份的哈希、当时同一步里结束的请求数和在跑请求数。
- **为什么能逐位比较**：两份来自同一批计算的同一块快照显存，只差“怎么拷”，数值必须完全相同；任何差别都是拷贝的时序或生命周期问题（读早了、被覆盖、被回收）。
- **还要检查的**：CUDA stream/event 依赖（旁路流等快照事件；`record_stream` 防止显存被提前复用）、内存生命周期（快照张量在旁路拷贝完成前不能被释放——在 verify 模式下额外 `torch.cuda.synchronize()` 之后再比较一次，确认两种时序给出同一结果）、并发安全（并发 1/8/32/64、文字和语音混合、带/不带 seed 混合、中止请求，沿用实验 11 的段落）。
- **CPU 检查**：用替身流和事件，构造“读早了”“被覆盖”的情形，确认 verify 模式能报出不相等（在改动之前失败、之后通过）。

### 判定（事先写定）

- 所有段的所有结束请求：逐位相等 100%、行数 100% 正确、0 报错 → **通过**，才放行 A/B/C 的性能对比（实验 11 原登记的 9 个运行）。
- 出现任何一处不相等 → **不通过**，只报告失败证据和定位信息，不做性能比较。
- 不能把实验 11 原来的结果改写成通过。

### 缺的证据和下一步

| 缺的 | 怎么补（成本） |
|---|---|
| I/O 是否阻塞 | 采样器每秒记 `/proc/pressure/{io,cpu,memory}` 和 NFS 客户端统计（`/proc/self/mountstats` 的增量）；几乎零成本，可以加进所有以后的运行 |

| 停顿时进程在哪 | 采样器检测到“服务日志 > 1 s 没有新行”时，对所有阶段进程跑一次 `py-spy dump`（只读，不停进程） |
