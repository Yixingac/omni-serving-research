## P0：talker 名额 32 → 64（登记于 2026-11-18 22:12，第一次运行之前）

原登记：`research/next_steps/p0_p3_experiment_plan.md` 的 P0 节（H0a/H0b/H0c、方案 A/B/C、参照 t2_k2_c4、3 个区组、种子 20261119）。

### 补充 1：新增方案 G（名额 64，CUDA graph 仍只录到 32）

- **为什么加**：sglang-omni 的 `generation_batch_policy.py` 让 `cuda_graph_max_bs` 默认等于 `max_running_requests`。所以方案 B 同时改了两件事：准入名额（32 → 64）和 CUDA graph 覆盖的批大小（≤ 32 → ≤ 64）。B 对 A 的差别不是严格的单变量效应。
- **怎么做**：`stages.talker.engine` 同时设 `max_running_requests: 64` 和 `cuda_graph_max_bs: 32`（两个都是 `EngineArgs` 里声明过的字段，后者在 `build_generation_batch_overrides` 里会单独生效）。批大小超过 32 的解码步走 eager。
- **怎么解释**（事先写定，只做描述，不产生新的“支持/反驳”判定）：
  - 准入效应 = G − A（名额放开，graph 覆盖不变）；
  - graph 覆盖效应 = B − G（名额相同，只差 33–64 的批有没有 graph）；
  - 两者都用 W3b 登记容量的配对差报告（3 个区组的均值和 t 区间）。某个效应在 3 个区组都 ≥ +5% 记作“有贡献”，3 个区组都在 ±2% 以内记作“没有可测的贡献”，其余记作“不确定”。
- 前提：G 的日志里确实有超过 32 个请求同时在跑，并且启动日志里 talker 的 graph 只录到 32。否则 G 无效，只报告原因。

### Erratum E-P0-G（2026-11-18 23:45，区组 1 的 G 运行之后、区组 2 之前）

方案 G 在固定版本上**无法启动**：talker 进程在启动时报 `ValueError: MiniCPM-o talker invalid generation batch policy: cuda_graph_max_bs must cover max_running_requests (32 < 64)`（`sglang_omni/scheduling/generation_batch_policy.py:376-382`），服务没有就绪就退出（运行 `20261118_ppv_p0_cap64_graph32_block1_a2_run01`，约 2 分钟，没有任何测量）。执行前的 CPU 检查只调用了 `build_generation_batch_overrides`（得到 graph 32、名额 64 的参数），没有调用启动时的 `validate_generation_batch_policy`，所以没有提前发现。

处理（按补充 1 已写的“否则 G 无效，只报告原因”）：
- G 记为 **BLOCKED（固定版本不允许 graph 上限低于准入名额）**，不打补丁绕过这个检查——它是实现明确禁止的组合，绕过以后的行为不能算“安全地独立控制”；
- 区组 2、3 用 `plan_ppv_p0_block{2,3}_a2_without_g.json`（其余三个方案保持原随机顺序）；
- 因为准入名额和 graph 覆盖在这个实现里**必须一起变**，方案 B 对 A 的差别只能写成“名额 32→64 连同 graph 覆盖 ≤32→≤64 的联合效应”，不能写成单变量的准入效应。补充 1 里“G − A”“B − G”的分解不报告。

### 指标定义（起点 → 终点）

| 指标 | 定义 |
|---|---|
| 单元延迟（unit lag） | 服务拿到这个单元全部输入的时刻（客户端发完含该单元最后一个样本的包；补零的最后一个单元取它和 `sglang.input_audio.end` 的较晚者）→ 收到这个单元的 `sglang.unit.done`。与上游 `benchmarks/duplex/serving.py` 相同 |
| 单元错过 | 单元延迟 > 1 s（一个单元的时长），或者一直没收到 `sglang.unit.done`。错过率 = 错过数 ÷ 计划单元数（失败会话的全部单元都算错过） |
| TTFA（每个用户回合） | 发完这句话最后一个包 → 收到“第一个首音频晚于这个时刻、且早于下一句话开始”的回答的第一个音频增量。没有这样的回答记 `no_response`（模型选择继续听），**不给数字**；话说完时模型还在说上一段，记 `overlapped_at_end` |
| 回复首音频延迟 | 回答的第一个音频增量到达 → 携带它的那个单元的“输入齐了”时刻（上游的 first audio，只含服务时间，不含模型“听”的单元） |
| 音频增量间隔 | 同一回答相邻两个音频增量的到达间隔 |
| 播放卡顿 | 播放器在回答第一个音频到达后等 r 再开始、按顺序播放；等不到下一段就是一次卡顿。r = 80 ms（主值，上游默认），0 和 250 ms 做敏感度；另报“不卡顿所需的最小起播缓冲” |
| 截止时间未满足 | 用户回合里 `no_response` 或 TTFA > D 的比例；D = 1 s（主值），0.5 s、2 s 做敏感度；同时报只看有回答的回合的比例 |
| 听/说 | 某个 `unit_id` 有音频增量 = 说；只有文字 = 只出字；都没有 = 听 |
| 打断（只在 R1） | 每第 3 个提问结束后 3 s 插入另一句提问。只有当时有回答正在出音频才算一次有效打断；停止延迟 = 被打断回答的最后一个音频增量 − 打断语句的第一个包。固定版本没有 `response.cancel`，所以这测的是“模型自己停下”的时间，不是系统取消延迟 |
| 分位数 | P50 至少 1 个样本、P90 至少 10、P95 至少 20、P99 至少 100；不够就写 N/A 并报样本数 |
| 资源 | nvidia-smi 0.2 s 采样（利用率、显存）；每进程 CPU 和 Linux 压力指标（1 s）；B 段的服务端请求事件 → `build_duplex_session_metrics` 的每阶段排队、执行、交接时间 |

### R0：全双工功能验证（1 张卡）

- **问题**：Can MiniCPM-o 4.5 deliver continuous, real-time audio responses through SGLang-Omni on an RTX A6000?
- **运行** `ppv_r0_duplex_functional`：默认 max_sessions 2；30 s 冒烟 → 1 个会话 300 s → 2 个会话 300 s（冒烟失败则后两段不跑），不开服务端事件。
- **通过条件**（全部满足才算通过，看到结果前写定）：
  1. 服务启动成功：`/health` 为 healthy，`/v1/realtime/capabilities` 返回 `native_full_duplex: true`；
  2. 1 个和 2 个会话的段都完成 300 s：每个会话发完全部计划的包、收到 `sglang.input_audio.drained` 和 `session.closed`（reason `client_closed`）；
  3. 没有致命错误：没有 `sglang.fatal` 的 error、服务进程没有退出或重启、客户端没有未处理异常；
  4. 收到有效音频增量：每个会话至少有 1 个带音频的回答，音频能解码、总时长 > 0、不是全静音（电平 > −60 dBFS 的块占多数）；
  5. 能提取单元延迟：每个会话 ≥ 95% 的计划单元收到 `sglang.unit.done` 并能对上发送记录。
- **另外报告，不影响通过**：单元错过率（上游的实时目标是 ≤ 1%）、TTFA、回答率、播放卡顿、节奏违规、GPU/CPU。功能通过但单元错过率 > 1% 写成“能跑但不实时”。
- **失败分类**：模型加载（ready 之前退出、权重/依赖错误）；显存（CUDA OOM、`max_sessions needs ... of thinker KV`）；协议（`not_supported`、`invalid_state`、`buffer_overflow` 等非致命错误，或缺少应有的事件）；模型行为（从不开口、只出静音、`context_exhausted`）；功能缺失（例如需要取消）。保存服务日志和客户端轨迹，不改版本。

### R1：单会话关键路径（R0 通过后，每个运行 1 张卡）

- **问题**：What determines the latency of the first spoken response?
- **运行**：`ppv_r1_duplex_block{1,2,3}`：冒烟 30 s；A（不开事件）和 B（开服务端请求事件）各 1 个会话 300 s，带打断回合；A/B 顺序区组 2 反过来。`ppv_r1_chat_ref_block{1,2,3}`：请求-响应参照，**同样 1 张 A6000** 上的默认语音流水线（`--code2wav.process code2wav`，即 plan v2 的 R8 副本，规避单进程崩溃），同一批提问（W3：语音进、语音出，max_tokens 64，提示“用一句话回答”），并发 1，A/B 各 48 个请求。
- **事先的预测**（Estimated，用来对照，不是判定规则）：
  - 单元延迟 P50 在 0.3–0.9 s（上游在 H200 上 1 个会话约 180 ms，A6000 按 2–4 倍慢估计，且语音阶段默认 FP32）；超过 1 s 的可能性不能排除；
  - 全双工 TTFA ≈ 等单元切出（0–1 s，平均约 0.5 s）+ 单元处理 + 模型再多听 k 个单元 × 1 s；
  - 参照路径的 TTFA ≈ 端到端（语音在 code2wav 做完后一次返回，实验 6），单卡上预计 2–3 s。
- **怎么比**：两条路径语义不同，报告时并列给出各自的工作量和语义：全双工从“话说完”开始计、回答长度由模型决定、用 demo 默认采样（temperature 0.7）；参照从“整段请求发出”开始计（真实应用里还要加端点检测的时间，本实验没有）、回答由 max_tokens 64 截断、temperature 0（W3 的设置）。同时报两边每个回答的音频秒数和文字长度。**不用 TTFA 的差别推出任何 kernel 或调度结论。**
- **分解**：B 段用服务端事件给出每单元每阶段（perception、thinker、talker、speech）的排队、执行、交接；报 1 个会话时占单元处理时间最多的阶段。B 对 A 的单元延迟 P50 差 > 10% 时，阶段数字标注“事件记录有可见开销”。

### R2：并发会话（R0 通过后）

- **问题**：What is the first stage or resource that limits real-time interaction as the number of sessions increases?
- **放置的决定规则**（看冒烟结果，不看正式数据）：
  1. 冒烟 `ppv_r2_smoke_ms8_1gpu`：max_sessions 8 单卡能启动、8 个会话 30 s 无失败 → 正式用 `ms8_1gpu`（档位 1/2/4/8，同一放置）；
  2. 否则正式用 `ms4_1gpu`（档位 1/2/4，单卡、默认显存比例、按满长会话预留 KV）+ `ms8_2gpu`（档位 4/8，thinker 单独占第 2 张卡、显存比例 0.85）；后者先过冒烟 `ppv_r2_smoke_ms8_2gpu`，过不了就把 8 个会话记 Blocked，并写明原因（显存或跨卡交接）。
  - 不采用“减小 thinker KV 预留来硬塞 8 个会话”：那样会话变长后会被拒绝，属于改变调度容量。
- **运行**：每个区组一次启动，档位从低到高各 180 s，开服务端事件；**停止规则**：某档有会话失败或单元错过率 > 1%，就不跑更高的档（写成负面结果）。3 个区组。
- **指标**：TTFA、单元延迟的 P50/P95/P99（3 个区组的会话合并，报样本数）；单元错过率；播放卡顿；截止时间未满足比例（1 s 主值，0.5/2 s 敏感度）；回答率；GPU 利用率和显存；每进程 CPU；每阶段排队（服务端事件）；会话错误、503 次数、平均同时在线会话数。
- **容量**（沿用上游）：没有失败会话、没有 503、没有节奏违规、单元错过率 ≤ 1% 的最高档。另报“截止时间未满足比例 ≤ 5%”的最高档（原计划 `robotics_experiment_plan.md` 第 3 节）；如果模型行为本身（多听几个单元）就让 1 个会话也超过，就写明这是模型的轮次决策造成的，不是服务容量。
- **“第一个先满的阶段”的判定**：在单元错过率第一次超过 1% 的档位（或者最高档），比较每个阶段每单元的“排队 + 执行”中位数相对 1 个会话时的增量，增量最大的阶段就是答案；同时看这个阶段所在 GPU 的利用率和进程 CPU 是否到顶，分清是 GPU 还是 CPU。
- **区组之间的差别**：报每个区组各自的 P50，区间用区组均值的 t 区间（自由度 2）。

## C1、C2：微基准（登记于 2026-11-18 22:55，任何 C1/C2 运行之前）

完整的规则、指标定义和预测在 `c1_c2_design.md` 第 5 节（与本节同一次提交），这里只列要点，便于核对：

- C1 的性能门槛不变（原登记）：P1 的 E 在 W3b 或 MIX 主组、3 个计时遍每一遍都比 D 低 ≥ 5% → 进入端到端；否则停止并逐项报告原因。
- **Erratum E-C1**：原正确性规则“P1 对 D 的差异不超过 D 自己重复的差异”在离线微基准里退化成“必须逐位相同”（D 是确定性的），而固定版本的打包路径设计上是 BF16，必然不同。修正版 C1-Q：波形长度正确且有限；MCD 对 FP32 参考的均值增量 ≤ 0.1 dB；ASR 完全一致段数最多少 1 段、合并 WER 最多 +0.5 个百分点。**原规则照算照报**，两个版本的结论都写进结果。
- C2：B（weight-norm 折叠）≤ 1 ulp / 逐位；C（channels-last）rel RMS ≤ 1e-4 且 MCD ≤ 0.01 dB；D（FP16 主体）MCD < 0.1 dB 且 ASR 同上；(a)+(b) < 3% 不做端到端；D 过质量门槛且 HiFT 时间 3 遍都 −20% 以上才是端到端候选。
- PESQ/STOI：运行环境里没有安装，事先声明不适用；用 MCD、波形误差和 ASR 回读代替（不事后挑指标）。
- 任何微基准改善只写成“局部 GPU 时间”，不写成端到端收益。

## R1/R2 分析口径补充（2026-11-18 23:51，写于分析任何 R1/R2 数据之前）

> 上面 R1、R2 的登记没有写细的计算口径，这里一次定下来；分析代码 `scripts/analysis/ppv_r1_report.py`、`ppv_r2_report.py` 照此实现。规则不因结果改动。

**R1**

1. **主数据段**：客户端指标（TTFA、单元延迟、回复首音频服务时间、音频增量间隔、播放卡顿、打断）以 A 段（不开事件）为主值，B 段并列报告。30 s 冒烟段不进分析，只当功能检查。
2. **合并**：每个区组一个会话。“合并”指把 3 个区组同名段的回合、单元、回复放在一起算分位数（N 与 N/A 规则照旧）；另报每个区组各自的 P50，以及 3 个区组 P50 的 t 区间（df 2）。
3. **重复运行**：同一区组有多次运行（编排器重试）时，用最后一次 status 为 ok 的运行；其余列为“排除的运行”并写明原因，不删除。
4. **TTFA 分解**（每个有回答的回合，全部用客户端 monotonic 时间）：t_end = 发完话语最后一个包的时刻；u0 = 含话语最后一个样本的单元 = ⌊(end_sample − 1) / 16000⌋；u1 = 回答第一个音频增量所属的单元（取增量的 `sglang.media_time.t_start_ms` / 1000）；ready(u) = 发完含单元 u 最后一个样本的包的时刻（补零的最后单元取它与 `sglang.input_audio.end` 的较晚者，同单元延迟的定义）。
   - (a) 等单元切出 = ready(u0) − t_end；
   - (b) 多听的单元数 k = u1 − u0，对应时间 ready(u1) − ready(u0)；
   - (c) 说话单元的服务时间 = 首音频到达 − ready(u1)（即回复首音频延迟）。
   - 三项之和恒等于 TTFA。k < 0（第一个音频来自话语结束前就已切出的单元）记为“提前开口”，单独计数，不进 k 的分布。u0 到 u1 − 1 之间的单元按“听 / 只出字 / 说”分别计数。
5. **阶段份额**（B 段，服务端请求事件）：每单元的“单元处理时间”= `ready_to_finished_ms`（`session_unit_ready` → `session_unit_finished`）。阶段 s 的份额 = Σ单元 (queue_s + service_s) ÷ Σ单元 ready_to_finished；交接（handoff）和“其余”（ready_to_finished − Σ(queue + service + handoff)）各算一类。
   - **主值只看“说”的单元**，因为 R1 问的是首段语音。“说”的单元按会话 id 和单元序号与客户端对齐（该 unit_id 收到了音频增量）；对不上时用服务端单元的 outputs 是否非空。
   - 全部单元的份额作为第二个数。只计 observed 的阶段；bypassed 的阶段不计时间，只报次数。
   - 服务端指标只能用运行时的 python（集群）算；算不了时标注“不可得”，不填 0。
6. **事件开销标注**：3 个区组合并后，B 段单元延迟 P50 与 A 段相差超过 10%（任一方向），阶段数字就加“事件记录有可见开销”。每个区组的差别另报，单个区组不触发标注。
7. **参照路径**：主值用 A 段的 48 个请求，B 段并列。
   - 每个请求报首音频时间（first_audio − sent）、端到端（done − sent）、音频秒数、文字字符数（`text_chars`）和 completion tokens；
   - 按题目（音频资产 id）与全双工的回合并列；
   - 出错或超时的请求只计数，不进分位数。
8. **D1 描述**：每个区组的 A、B 段各报单元延迟 P50/P90 和 TTFA P50，以及区组 1 相对区组 2、3 均值的差（%），只描述，不改任何结论。

**R2**

9. **合并**：每个档位把 3 个区组的会话合并后，算分位数、错过率和截止时间未满足比例。
   - 9b. **用哪次运行**：每个区组（以及每个冒烟）用最后一次运行，不论它的状态；每一档按它实际留下的数据判断（中途服务退出的那一档有失败会话，自然不达标；更低的档已经完成的数据照常使用），运行状态照实报告。和 R1 不同，这里不要求 status 为 ok，因为失败的冒烟和中途失败的档位本身就是结果。
10. **达标与容量**：一档“达标”须同时满足：3 个区组都运行了这一档；3 个区组都没有失败会话、没有 503（连接被拒）、没有节奏违规；合并后的单元错过率 ≤ 1%。
    - 容量 = 从最低档起连续达标的最高档（与上游相同的 takewhile）。全部档位都达标时，写“≥ 最高档（未触顶）”。
    - 截止时间档同理：同样要求 3 个区组都运行、都没有失败会话（失败会话没发出去的回合不进分母，不加这条就会把失败藏起来），并且合并后的截止时间未满足比例（所有发出的用户回合，no_response 算未满足）≤ 5%。D = 1 s 为主值，0.5 s、2 s 做敏感度。
11. **停止规则**：某档在某个区组被跳过（上一档有失败会话或错过率 > 1%），就在该区组记为“跳过”，这一档不能算达标。
12. **两种放置**：容量按放置分别报告（ms4_1gpu、ms8_2gpu 或 ms8_1gpu 各自的档位）。跨放置只做描述性对比（例如 4 个会话在 1 卡和 2 卡上），不合并。
13. **第一个先满的阶段**：
    - 基准档 = 该放置的最低档：ms4_1gpu 和 ms8_1gpu 是 1 个会话；ms8_2gpu 没有 1 个会话的档，用 4 个会话。
    - 目标档 = 第一个合并错过率 > 1% 的档，没有就用最高档。
    - 取每阶段每单元 queue + service 的中位数（只计 observed），用目标档减基准档，增量最大的阶段就是答案；同时列出所有阶段的增量。
    - 资源判定沿用 P0 H0b 的阈值：该阶段进程 CPU 的 P90 ≥ 95%（一个核）且所在 GPU 采样利用率均值 < 80% → CPU 受限；所在 GPU 利用率均值 ≥ 90% → GPU 受限；否则写“都没到顶（不确定）”。
    - 单卡放置时所有阶段共用一张卡，GPU 利用率是整卡的。
    - 进程与阶段的对应取自请求事件文件名 `events_<stage>_<pid>.jsonl`。GPU 与阶段的对应：用了 `--thinker.gpu 1` 时 thinker 在第二张卡，其余阶段在第一张；nvidia-smi 的序号按升序对应服务的 GPU 列表。
14. **区组区间**：每个区组的统计量是该区组在该档合并后的 P50。区间 = 3 个区组 P50 的均值 ± t(0.975, 2) × SD / √3（t = 4.303）。
15. **冒烟和放置**：按登记的放置规则，从冒烟结果推出应当使用的放置，并检查实际运行的放置是否与之一致；冒烟运行不进正式结果。失败按服务日志和错误信息里的关键字分类（显存、模型加载、协议、模型行为、功能缺失），并附上匹配到的那一行作为证据。
16. **模型行为造成的截止时间未满足**：在最低档里，如果未满足的回合过半属于以下两种情况之一，就写“主要是模型的轮次决策，不是服务容量”：一是 no_response；二是 k ≥ 1，且 (a) + (c) ≤ D（只算服务部分本来能按时）。
