# 限制和负面结果

> 本轮所有没跑成、没通过、没有改善、不稳定或证据不足的情况都记在这里，按出现的先后写，不删。每条写清楚：发生了什么、证据在哪、对结论有什么影响。英文的学术表述在 `final_experiment_results.md` 各节的 Limitations 里。

## 2. 测量方法本身的限制

| 编号 | 限制 | 影响到的结论 |
|---|---|---|
| M1 | 方案 A、B 的 talker 进程 CPU 在所有负载下都在 100–108%（一个核；2+2+4 参照在 W3b 256 时为 87–93%），低负载时也一样，更像调度循环的忙等，而不是真的被计算占满 | P0 的 H0b 里“talker CPU ≥ 95%”这一条区分不了“CPU 受限”和“忙等”；按登记规则照判，但结论要加这条说明 |
| M2 | 全双工客户端有 0.63% 的音频包（1 个会话那段 0.75%）比计划晚 80 ms 以上（最多晚 1.19 s），可能是客户端事件循环被写记录等操作阻塞 | 单元延迟按实际发出时间算，不受影响；但服务端在那些时刻收到的输入是成批的 |
| M3 | TTFA 的样本按“用户回合”计，每 5 分钟每个会话只有约 14 个回合 | P95、P99 写 N/A；只报 P50/P90 和样本数 |
| M4 | nvidia-smi 的 GPU 利用率和每秒一次的全双工负载混叠，读数大多为 0 | 全双工的 GPU 利用率不报，改报功耗和服务端阶段时间 |
| M5 | 全双工的单元延迟是双峰分布（说话单元约 350 ms、只听单元约 74 ms），所有单元合在一起的中位数随“说话单元占比”跳动 | 比较不同档位时按单元类型分开报 |
| M6 | R3 筛选里 1、4 个会话的 15 个格子，nvidia-smi 利用率整段或几乎整段读 0%（零读数占 77–100%，功耗 140–224 W），同负载的配对格子一个 0%、一个 88% | R3 的利用率只在饱和格子里可用（那里零读数为 0，并发 1 时功耗 283–291 W 互相印证）；分类规则没变，另报功耗 |
| M7 | R3 的帧是合成的（PNG 约 2.5 KB），比真实摄像头的 JPEG/H.264 小得多；图像编码器的“服务时间”是在一张被所有阶段共用的 GPU 上从派发到完成，分不开它自己的计算和等 GPU 的时间 | “CPU 预处理不是瓶颈”只对这么小的帧成立，CPU 解码成本是下限；“时间花在图像编码器上”是阶段定位，不是 kernel 级的归因 |

## 3. 没有通过、没有改善或证据不足的结果

| 编号 | 结果 | 证据 | 对报告的意义 |
|---|---|---|---|
| N1 | C1：登记的候选（BF16 打包 + 编译）速度达标（E −13% 到 −42%），但音质门槛**没过**（MCD 比稠密路径高 1.01 dB）；按“正确性先行”不下性能结论、不做端到端 | `results/c1_microbench.json`、`results/c1_quality.json` | 只能说“打包在微基准里更快、但固定版本的 BF16 打包会变差音质”；FP16 打包（探索性）速度相同、音质在门槛内，需要下一轮登记后再验证端到端 |
| N2 | C1 的质量门槛本身噪声很大：数学上等价的稠密路径开/不开 CUDA graph（D 对 D_ng）MCD 就差约 4.1 dB，D_ng 还没过 ASR 那一条 | 同上 | 质量门槛只能做方案之间的相对比较；ASR 那一条比运行间的随机差别还紧，区分力弱 |
| N3 | C2：weight-norm 折叠逐位正确但没有可测的时间收益；channels-last 和 FP16 没过数值门槛；FP16 在两个批处理组反而慢 31–50%（W3L 组 −2…+23%） | `results/c2_microbench.json`、`results/c2_quality.json` | HiFT 的编译期优化方向按登记规则停止；“HiFT 受启动开销限制”只是推算加假设 |
| N4 | C1 在开环、未饱和的 2+2+4（每批约 1.2 个请求）上收益约 −1% | `results/c1_microbench.json` 的 `exp10val` 组 | 打包只在批处理、长度混合时有用；实时低并发场景收益很小 |
| N5 | R1：打断后被打断的回答中位数还要继续 5.1 秒（最长 11.6 秒）；固定版本没有 `response.cancel` | `results/r1_summary.json` 的 `barge_in` | 机器人场景的“打断”在固定版本上不可用 |
| N6 | R0–R2：全双工在 1 秒内开口的回合只占 25%–50%（R1 25%、R0 29%、R2 的 1 个会话档 50%），多数未满足来自模型的轮次决策（多听一个单元或不回答） | `results/r1_summary.json`、R2 报告 | 截止时间未满足不能当作服务容量不够 |
| N7 | R3 筛选：登记的预测（`clip` 在 16 个会话、≥ 1 帧/秒时卡在 CPU 预处理，提高预处理并发有帮助）不成立：5 个饱和格子都是“GPU 受限”，预处理只占服务端时间的 2–8%；并发 4 在 18 个格子里都没有达到“有改善”（丢帧变化 −3.5…+1.2 个百分点，首个回答 P95 −14…+9%） | `results/r3_screen.json` | 提高 CPU 预处理并发不是这条路径的杠杆；3 个区组的确认运行排队中，最终判定以确认为准 |
| N8 | R3：“跟得上帧率”不等于“回答新鲜”：单张 PNG、16 个会话 × 0.5 帧/秒按规则不饱和（丢 4.4%），但首个回答中位数 1.50 秒（P95 1.86 秒），约是 1 个会话时中位数的 10 倍 | 同上 | 机器人场景要同时看丢帧和每帧的回答延迟 |
