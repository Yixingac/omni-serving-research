> 2026-11-18。本文是计划，**一个实验都还没有跑**。英文的研究介绍在 `robotics_application_intro.md`；本文讲具体怎么测。
> 代码事实指 sglang-omni `520b49ee`；全双工的细节来自源码审计（`sglang_omni/serve/realtime/`、`sglang_omni/models/minicpm_o/native_config.py` 等），没有在我们的机器上验证过。

## 0. 先用 8 个问题说清楚

| 问题 | 回答 |
|---|---|
| 1. 想解决什么 | 一个“边看边听、会调用工具、用语音回答、能被打断”的机器人助手，在共享 GPU 上同时服务多个交互时，首段音频和打断响应能不能做到实时；限制它的是哪个阶段 |
| 2. 为什么认为有问题 | 现在测过的请求-响应路径上，语音在三个阶段都做完后一次性返回，首段音频 ≈ 端到端，低负载也约 2 秒（实验 6）；高负载时 code2wav 排队占大头 |
| 3. 哪个实验发现的 | 实验 6、9（首段音频）、实验 14（视频预处理）、实验 19（Agent 负载） |
| 4. 别人怎么做 | SGLang-Omni 的原生全双工（1 秒一个单元，模型自己决定说还是听）；OmniCast（按播放进度和首音频优先级调度、处理打断）；Metronome（全双工会话的 KV 窗口和准入）；VoxServe（按 TTFA 和卡顿 SLO 调度） |
| 5. 怎么验证 | 先做全双工的功能验证，再用可复现的模拟传感器流测会话数扫描；请求-响应路径做同样的对话，作为对照 |
| 6. 可能有多少收益 | 现在说不出数字。上游在 H200 上报告单元延迟 p50 180→282 ms（1→8 个会话），我们的 A6000 和默认放置可能差很多（Unknown） |
| 7. 结果不好能学到什么 | 如果 A6000 上默认全双工连 2 个会话都达不到实时，结论就是“交互路径受单卡多阶段争用限制”，正好对接实验 7、9 的放置研究 |
| 8. 值得继续吗 | 值得：这是机器人应用和现有吞吐研究之间缺的那一块数据；功能验证成本低 |

## 2. 两条路径的数据流

### 2.1 请求-响应路径（已测）

摄像头/麦克风 → 客户端打包一轮输入 → `/v1/chat/completions` → coordinator（准入时轮转绑定各阶段副本）→ 预处理（CPU：解码视频、算 mel）→ 编码器（thinker 进程、GPU）→ thinker（逐 token，文字流式返回）→（如果是工具调用）客户端执行工具 → 下一次请求 → … →（最终回答）thinker 写完 → talker 生成全部语音编码 → code2wav 整段合成 → 一次返回音频 → 播放。

- 串行：同一请求的 thinker → talker → code2wav。
- 已经重叠：不同请求在不同阶段并行；文字边写边返回。
- 会话状态：只在客户端（对话历史）；服务端只有 thinker 的前缀缓存（LRU），且同一会话的连续请求会轮流落到不同 thinker 副本（`sglang_omni/pipeline/replicas.py:269-315`）。

### 2.2 原生全双工路径（未测，按源码）

启动：`--variant session --enable-realtime`。默认四个阶段（感知、thinker、talker、语音）都在 GPU 0 上（显存比例 0.12/0.52/0.15/0.15），最多 2 个会话。

- **输入持续到达**：客户端按 80 ms 包送音频（`benchmarks/duplex/client.py`），服务端凑成 1 秒单元；图像可以随时追加。
- **thinker 持续处理**：每个单元做一次“听还是说”的决定；会话在服务端是 SGLang 的流式会话，历史上限 8,192 token。
- **talker 什么时候开始**：模型决定“说”的单元；语音阶段按单元合成，跨会话凑批。
- **流式音频**：每个单元产出音频增量（24 kHz）。
- **打断**：模型驱动；客户端的 `response.cancel` 在 520b49ee 不支持。
- **阶段重叠**：同一会话里，下一个输入单元的感知可以和上一个单元的合成重叠（设计如此，**未测**）。

**再次强调**：实验 1–19 的结论只适用于 2.1。全双工是不同的流水线配置（单卡、按单元合成、流式会话），瓶颈可能完全不同。

## 3. 指标（起点和终点）

| 指标 | 起点 | 终点 | 备注 |
|---|---|---|---|
| TTFT | 客户端发出请求 | 收到第一段非空文字 | 已有 |
| TTFA（请求-响应） | 客户端发出请求 | 收到第一个音频块 | 已有；目前等于端到端 |
| TTFA（全双工） | 用户这一句话的最后一个音频包发出 | 收到第一个 `response.output_audio.delta` | 新定义；需要知道“这一句话什么时候结束”，由回放脚本给出 |

| 阶段排队、GPU kernel 忙碌、CPU | — | — | 已有的事件、nvidia-smi、profiler、每进程 CPU |

## 4. 负载：可复现的模拟传感器流

一个“机器人会话”的脚本（合成，种子固定）：

1. 每 1 秒一张 640×360 的场景图（合成的彩色物体，沿用实验 14 的视频生成方式；可设 0.5/1/2 fps）。
2. 用户说一句问题（合成语音 2–5 秒），内容引用画面（“左边有几个红色的圆？”）。
3. 模型可能先发一次文字工具调用（模拟“查物体数据库”，延迟对数正态，中位数 0.3 s），再用语音回答。
4. 30% 的回合里，用户在机器人说话的第 1–2 秒打断（另一句合成语音）。
5. 会话持续 N 轮（主值 10 轮），轮间隔是用户思考时间（对数正态，中位数 2 s）。

两条路径用同一个脚本：请求-响应路径把每一轮打包成一次请求（图像 + 语音 + 历史），全双工路径按真实时间流式送。

## 5. 实验（按顺序；每个只回答一个问题）

### R0 全双工功能验证（最先做，约 1 小时 GPU，1 张卡）

- 问题：MiniCPM-o 的 `--variant session` 在 A6000 + 520b49ee 上能不能跑起来、单会话能不能稳定流式出声。
- 做法：按上游 cookbook 启动；用 `benchmarks/duplex/client.py` 回放一段合成对话；检查音频增量、单元事件、会话关闭、异常。
- 通过条件：1 个和 2 个会话各 5 分钟无错误，音频连续，单元延迟有数。
- 失败处理：记录失败证据；判断是否要换到上游较新的提交（`response.cancel` 等功能在 main 上），并单独登记版本差异。

### R1 单会话的交互延迟分解（R0 通过后）

- 问题：一个会话独占时，TTFA、单元延迟、打断延迟各是多少，时间花在哪个阶段。
- 对照：同一对话走请求-响应路径（2+2+4 放置）。
- 指标：第 3 节全部；全双工开阶段事件。
- 期望（Hypothesis）：全双工的 TTFA 远低于请求-响应路径的约 2 秒；打断在 520b49ee 上只能靠模型自己停。

### R2 并发会话扫描

- 问题：同时进行的会话从 1 加到 8（需要改 `max_sessions`），截止时间未满足比例和卡顿怎么变，先满的是哪个阶段。
- 设计：默认单卡放置；再试把 thinker 和语音阶段分到两张卡（如果配置支持）。3 个区组。
- 指标：并发会话容量、单元延迟 P50/P99、阶段排队、GPU 忙碌、CPU。
- 失败的可能：默认放置在 2 个会话时就不达标——这本身就是结果，并转向放置实验。

### R3 持续视频输入的瓶颈

- 问题：持续送图像时，CPU 预处理、抽帧、编码器哪个先满。
- 依据：实验 14（10 秒视频 87% 时间在 CPU 预处理，每副本一次一个）。
- 设计：请求-响应路径上，图像帧率 0.5/1/2 fps × 会话数 1/4/16；对照 `--preprocessing.factory.max_concurrency` 1 和 4（上游参数，未测）。
- 指标：预处理排队和执行时间、编码器时间、GPU 忙碌、每进程 CPU。

### R4 机器人会话的工作集和 KV 容量

- 问题：多模态会话的上下文之和会不会超过 thinker 的 KV 池（每副本 127,039 token，实测），超过以后工具等待和用户思考是否导致重算。
- 这是 `thunderagent_flashstates_related_work.md` 的假设 B 的第一步，只测量，不改调度。
- 设计：请求-响应路径，2+2+4；会话数 8、16、32、64、128；每轮附 1 张图（最多 9 个切片 × 64 token）。
- 指标：每个 thinker 副本的活跃上下文之和 ÷ KV 容量、前缀命中率、每轮重算 token 数、编码器缓存命中、TTFT、会话完成时间。
- 判定：比值始终 < 0.8 → 结论是“对这个模型和卡，会话级缓存管理不需要”，停止这个方向；> 1 → 做假设 B 的第二步（会话粘性绑定）。
