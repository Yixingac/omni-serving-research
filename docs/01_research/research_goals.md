# 研究目标

## 背景

Omni 模型把多种输入（文本、语音、图像、视频）和多种输出（文本、语音）放进一个系统。以 MiniCPM-o 4.5 和 Qwen3-Omni 为例，一个“听问题、用语音回答”的请求依次经过：输入预处理（CPU 上解码音频、抽视频帧）、音频或视觉编码器、Thinker（语言模型，先生成文本）、Talker（把文本变成语音 token）、Code2Wav（把语音 token 变成波形），最后以流式方式送回客户端。

SGLang-Omni 把这些阶段放在不同的进程里，阶段之间通过消息传递数据。每个阶段可以放在指定的 GPU 上，部分阶段可以复制多份。这带来了文本 LLM Serving 里不常见的问题：阶段之间速度不匹配时的排队、CPU 预处理让 GPU 等待、多张 GPU 上的放置选择，以及阶段之间的数据传输。

另一方面，越来越多的请求来自 Agent：Agent 的一次任务包含多次模型调用和工具调用，后一次调用依赖前一次的结果，中间还有工具执行和用户思考的时间。这种负载的到达模式与“N 个并发客户端不停发独立请求”的常规压测不同。

## 目标

1. **刻画负载**：记录真实运行的 Agent 怎样使用 Omni 服务：一次会话有几次模型调用、几次工具调用，请求之间隔多久，突发程度如何，各模态占多少。
2. **找到瓶颈**：在固定硬件上测量每个阶段的排队时间和执行时间，确认在不同负载（文本、语音输入、语音输出、视频）和不同并发下，哪个阶段决定了延迟和吞吐。
3. **解释 GPU 空闲**：区分 GPU 空闲的几种来源：请求之间的依赖（Agent 在等工具）、CPU 预处理、调度间隙、阶段之间的等待。前两种可能是负载本身的性质，不一定是系统的缺陷。
4. **比较多 GPU 放置**：在相同 GPU 预算下比较完整副本、阶段拆分、只复制瓶颈阶段等方案，并测量阶段间通信的代价。增加 GPU 带来的提升，和相同预算下改变放置带来的提升，要分开报告。
5. **给出可验证的优化方向**：只提出有测量数据支撑、且可以用对照实验检验的假设。

## 不在范围内（第一阶段）

- 修改模型本身或训练。
- 在没有对照实验的情况下声称某种调度或放置“更优”。
- 声称研究的新颖性：需要先完成相关工作调研（`prior_work.md`），并与导师讨论。

## 与 PR #1 研究计划的关系

PR #1 提出了八周、四个阶段的计划：理解负载 → 找瓶颈 → 研究拆分部署 → 尝试一个优化。本分支实现前两个阶段所需的基础设施（trace、回放、编排、测量），并开始第一批 A6000 测量。PR #1 的内容保持不变。
