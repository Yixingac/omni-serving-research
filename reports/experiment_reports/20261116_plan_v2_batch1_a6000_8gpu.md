- 计划：`docs/04_experiments/plan_8gpu_v2.md`（阶段 0、A、B）；配置由 `scripts/slurm/make_plan_8gpu_v2.py` 生成。

- 节点：共享 `gpu` 分区里的一台 8×A6000 机器（下称“第一批节点”）。GPU 型号、NVLink 配对（0-3、1-2、4-5、6-7）、CPU 型号都与 compute-03 相同。驱动是 570，需要 cuda-compat；compute-03 是 580。
- 代码：本仓库 22911f7，sglang-omni 520b49ee。模型 MiniCPM-o 4.5，输入都是合成数据。

标注：**Measured** 实测；**Derived** 由实测计算；**Hypothesis** 待检验的解释；**Unknown** 不知道。

## 摘要

1. **8 卡最好的分法是 S2:6**，即一个服务里 2 个 thinker 副本加 6 个 talker 副本。
   - 闭环最高 19.4–19.7 请求/秒（Measured，两次运行）。
   - 开环在 23.3–23.7 请求/秒时，仍然全部满足 SLO（Measured）。所以它的 SLO 容量超过 23.5 请求/秒，比测到的范围还高（Derived）。
   - 8 个完整副本（R8）在 16.7–16.8 请求/秒以上就离开 SLO（Derived）。
   - 也就是说，同样 8 张卡，只换放置方式，满足 SLO 的吞吐至少多 40%（Derived）。
2. **4 卡最好的是 S1:3**：SLO 容量超过 11.7–12.3 请求/秒，R4 只有 8.6–9.4（Derived）。
   - 2 卡时，高负载下两个完整副本（R2，4.4）比拆分（P1，3.8）好；低负载下拆分的延迟更低（Measured）。
3. **负载类型会改变最佳放置**（Measured）。
   - 混合负载里 60% 的请求用不到 talker。S2:6 在闭环并发 256 时 thinker 排队，三类请求的 TTFT p90 都在 3 秒左右；P4 是 0.23–0.28 秒，R8 是 0.29–0.40 秒。
   - Agent 负载几乎全是短文本请求：R8 延迟最低，S2:6 最高。
   - 第二批正在补测更偏 thinker 的布局（S4:4、S3:5、S5:3、S6:2），以及加长的 Agent 实验。
4. **code2wav 放在单独进程后没有崩溃**。用了这个设置的 31 个实验，在 8 张卡上共运行约 6 小时，一次崩溃都没有（Measured）。默认配置的单卡对照 31 分钟崩溃 4 次，即 7.7 次/小时，27% 的请求失败（Measured）。
5. **有五个测量问题**，已经修复或在第二批补测，见第 8 节：
   - Y0 的点对点测试没测到东西；
   - 客户端 CPU 指标是错的；
   - 每个实验报告里默认的 goodput 标准不适合 MiniCPM-o；
   - 闭环每个并发槽只发 2 个请求，低估了容量；
   - Agent 实验每档太短。

## 3. A：8 卡放置（W3b）

### 3.1 闭环

每档 max(96, 2×并发) 个请求，两次运行。“满足 SLO 的速率”指开环下最高的一档提供速率：从最低档到这一档，每档都有 ≥ 95% 的请求满足 SLO。SLO 是端到端 ÷ 输出语音秒 ≤ 0.5，且 TTFT ≤ 1 秒。

| 布局 | 闭环最高吞吐，请求/秒（Measured） | 并发 64 时 e2e 中位数 s（Measured） | 满足 SLO 的最高速率，请求/秒（Derived） |
|---|---|---|---|
| R8：8 个完整副本 | 18.71 / 18.54 | 4.3 / 4.4 | 16.8 / 16.7 |
| P4：4 对拆分服务 | 15.32 / 15.22 | 3.6 / 3.4 | 15.3 / > 18.3 |
| S1:7 | 16.71 / 16.37 | 3.1 / 3.2 | > 20.1 / > 19.6 |
| **S2:6** | **19.72 / 19.39** | **3.0 / 3.0** | **> 23.7 / > 23.3** |
| S3:5 | 17.02 / 17.12 | 3.1 / 3.1 | > 20.4 / > 20.6 |
| S4:4 | 14.40 / 15.23 | 3.4 / 3.4 | > 17.3 / > 18.3 |

- **测试范围不够。** “>”表示测到的最高一档仍然满足 SLO，真实容量更高。开环的最高一档是闭环容量的 120%，而闭环本身低估了容量（第 8 节第 4 条）。
  - 例：S2:6 在提供 23.7 请求/秒时，实测吞吐 23.1，e2e/语音秒 p90 只有 0.30。
  - 第二批的 v2b_aoh_* 让 6 种布局都用 16–40 请求/秒的同一组绝对速率重测。
- **R8 的延迟在各个负载下都最高**（Measured）。
  - 开环 9.4 请求/秒时，R8 的 e2e 中位数是 3.8 秒，S2:6 在 9.9 请求/秒时是 2.2 秒。
  - Hypothesis：R8 每张卡上 thinker、talker、code2wav 三个阶段争用同一张 GPU。开环阶段 R8 的采样利用率是 98–99%。
- **重复性**（Measured）：两次运行的闭环最高吞吐相差 0.6%–5.6%，在计划规定的 10% 噪声范围内。差得最多的是 S4:4（14.40 和 15.23）。

### 3.2 各角色 GPU 的忙碌程度

开环阶段的平均值，采样利用率指有 kernel 在跑的时间比例，不是 SM 利用率（Measured）：

| 布局 | thinker 卡 | talker 卡 |
|---|---|---|
| P4 | 85% | 93% |
| S1:7 | 72–73% | 81–82% |
| S2:6 | 79% | 90–91% |
| S3:5 | 84% | 91% |
| S4:4 | 85–86% | 91–93% |
| R8 | 98–99%（每卡同时有两个阶段） | |

- talker 卡在每种布局里都比 thinker 卡忙，和 Job 409712 的结论一致：拆开以后瓶颈在 talker 一侧。
- S1:7 两边都不满，但闭环在 16.5 请求/秒就到顶了。Hypothesis：单个 thinker 副本的调度或批处理成了限制，而不是它的 GPU 算力。第二批的高负载开环会检验。

### 3.3 跨节点对照（第二批，正在跑）

S2:6 在 compute-03 上的闭环最高吞吐是 19.86 请求/秒，第一批节点上是 19.72 和 19.39；并发 256 的 e2e 中位数是 8.9 秒，第一批是 9.1 秒（Measured）。所以换节点和驱动后，结果差别在 2.4% 以内。R8 的对照还在跑。

## 6. B2：大规模 Agent（初步，每档太短）

**会话的样子**（Measured）
- 文本 Agent 每个会话中位数是 2 个模型请求：一次工具调用，加一次回答。
- 工具在进程内、几乎不花时间，中位数 35 微秒。
- 每个请求约 387 个输入 token、23 个输出 token。
- 所有档的任务成功率是 98.4%–100%。

**每档太短**（Measured）：会话总数只是并发的 2 倍，每档只持续 6–40 秒，测到的多半是升温和收尾，不是稳定状态。下表只能看相对高低。

| 布局 | 文本 Agent，并发 512：单次请求中位数 / p90 s | 会话中位数 / p90 s | 前缀缓存命中 |
|---|---|---|---|
| **R8，按在途请求最少路由** | **1.76 / 2.75** | **3.45 / 4.19** | 0.86 |
| R8，按会话固定路由 | 1.79 / 2.76 | 3.45 / 4.30 | 0.88 |
| P4 | 3.06 / 4.27 | 6.26 / 7.38 | 0.87 |
| S2:6 | 6.45 / 8.08 | 13.16 / 14.55 | 0.86 |

- **B-H2 方向成立**：Agent 负载几乎都是短文本请求，thinker 多的布局延迟低。
- **B-H3 效果很小**：按会话固定路由只把前缀缓存命中率提高 1–2 个百分点，延迟没有差别。Hypothesis：命中主要来自所有会话共享的系统提示词和工具说明；每个会话只有 2 个请求，会话内部能复用的部分很少。
- **工具延迟**：S2:6 上 256 个会话时，工具延迟 0、0.5、2 秒三档的单次请求中位数分别是 3.37、3.05、2.10 秒，会话时长相近（6.4–7.3 秒）（Measured）。会话花更多时间等工具时，同时在模型里的请求变少。各个 GPU 池的空闲比例要和 GPU 时间线对齐后再分析。
- 第二批的 v2b_b2l_* 把每档的会话数加到并发的 8 倍（512 并发时 4 倍），每档约 2–3 分钟。

## 8. 测量问题和处理

1. **Y0 的点对点测试什么都没测，却报告成功。**
   - 原因：`nvidia-smi topo -m` 即使输出到管道，表头也带下划线控制码（`\x1b[4m`），解析器找不到表头。
   - 已修复（9f77ed4）：先去掉控制码；能看到多张卡却解析不出 GPU 对时直接失败。
   - 第二批在 compute-03 上重测了：NVLink 对直接拷贝 52.6 GB/s，NCCL all-reduce 43 GB/s。其余 24 对只走 PCIe，直接拷贝只有 2.7 GB/s，比 NCCL 关掉点对点、经主机内存中转的 14.6 GB/s 还慢约 5 倍（Measured）。这台机器上 PCIe 点对点路径的性能有问题，原因不知道（Unknown）。
2. **“客户端 CPU”指标是错的。**
   - 原因：实验 runner 是服务进程的父进程，采样器在同一次采样里，把每个服务进程在“客户端”组里又读了一遍。psutil 在几乎为零的时间间隔上算 CPU 比例，结果是时钟节拍噪声，最高到 2700%。
   - 已修复（9f77ed4）：每个进程只算进第一个包含它的组。
   - 修复后在 compute-03 上跑了一次 S2:6，闭环最高约 20 请求/秒。这次运行里客户端 CPU 的中位数是 0.23 个核，p90 0.36 个核，最高 0.97 个核（Measured）。
   - Job 409712 里“客户端约 1.4 个核”的结论用的是同一个采样器，同样受这个错误影响，不再成立。所以当时以此为理由的多进程客户端（P1），现在没有证据说明需要。
   - 开环记录里还有发送延迟（计划发送时间到实际发送时间）：第一批所有开环档的 p90 都 ≤ 0.01 秒，说明客户端跟上了发送节奏（Measured）。
3. **默认 goodput 的标准不适合 MiniCPM-o。**
   - `analyze_experiment.py` 默认要求首个音频 ≤ 2 秒。MiniCPM-o 的音频在最后一次性返回，所以低负载时也只有约 40% 的请求“达标”。
   - plan v2 用的是端到端 ÷ 语音秒 ≤ 0.5，且 TTFT ≤ 1 秒。本报告的 W3b 数字都按这个标准重新分析过。
4. **闭环低估了容量。**
   - 每个并发槽只发 2 个请求，并发越高，开头升温和结尾收尾占的比例越大。例：S2:6 闭环并发 256 时 19.7 请求/秒、e2e 中位数 9.1 秒；开环 23.7 请求/秒时 e2e 中位数只有 3.2 秒。
   - 开环速率是按闭环容量换算的，所以大部分池化布局的开环没有测到离开 SLO 的那一档。第二批用绝对速率补测。
5. **B2 每档太短**，见第 6 节。第二批已加长。

原计划第二批的 D（回放方法）、E（Qwen3-Omni）、F（视频和 CPU）、G（拓扑）还要准备配置和代码，准备好后通过 plan.d 追加。

## 10. 局限

- 只有一个模型（MiniCPM-o 4.5），输入都是合成数据。
- “满足 SLO 的速率”受开环档位粒度限制：相邻两档之间的真实拐点不知道。
- GPU 采样利用率不等于 SM 利用率，只用来比较不同角色的卡谁更忙。
- 第一批节点和 compute-03 的驱动不同，S2:6 的对照只差 2.4% 以内，R8 的对照还在跑。
