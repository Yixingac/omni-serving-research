## 摘要

1. **小 batch（并发 1、2、4、8）时，放置方式不影响延迟**（Measured）。
   - 四种布局（S2:6、S1:7、P4、R8）每一档都是 100% 请求满足 SLO。
   - TTFT 中位数约 50 ms，e2e 中位数 1.5–2.2 s，e2e/语音秒 p90 为 0.16–0.17（SLO 是 0.5）。
   - 并发 8 时，吞吐为 3.5–3.7 请求/秒。
2. **小 batch 时没有排队，时间全花在三段串行的解码上**（Measured）。
   - 以 S2:6、并发 8 为例，每个请求的服务端时间（中位数）是：thinker 1.28 s（约 64%）、talker 0.53 s（约 26%）、code2wav 0.16 s（约 8%）。
   - 排队和阶段之间的传输加起来约 10 ms。
   - thinker 每个 token 用 26–27 ms，从并发 1 到并发 8 都不变。
   - thinker 是 8B 级的语言模型（36 层，hidden 4096），每生成一个 token 要读约 15 GB 权重（Derived，按模型配置估算）。按 A6000 标称带宽 768 GB/s，下限约 20 ms/token（Derived）。实测 26 ms，已经接近这个下限。
   - 所以小 batch 的延迟由显存带宽和串行结构决定，换放置方式没有用（Derived）。
   - MiniCPM-o 的语音是在最后一次性返回的，首段音频要等 1.5–2.6 s，和 e2e 一样（Measured）。对实时语音来说，这是最该降的指标。
3. **大 batch 时，在同一绝对速率下 S2:6 和 S1:7 最好**（Measured）。
   - 开环速率 16–40 请求/秒，每档 90 秒。
   - SLO 容量（Derived，速率步长 4 请求/秒）：S2:6 和 S1:7 是 24，S3:5 和 S4:4 是 20，P4 和 R8 是 16。
   - 与第一批一致：第一批 S2:6 超过 23.5，R8 为 16.7–16.8。
4. **大 batch 时的等待点，每种布局不同**（Measured，第一批闭环 16–256 的阶段分解）。
   - **R8**：thinker 和 talker、code2wav 挤在同一张卡上。并发 256 时，thinker 每 token 要 81 ms，是小 batch 时的 3 倍，可每个副本里平均只有约 10 个请求。
   - **S2:6 和 P4**：thinker 独占 GPU。S2:6 的 thinker 即使每个副本平均有 25 个请求在跑，每 token 也只要 34 ms。
     - 等待转到了与 talker 同卡的 code2wav 上。并发 256 时，code2wav 中位数 5.6 s（S2:6）和 8.5 s（P4），占 e2e 的六成以上。
     - code2wav 在高负载时会把多个请求合成一批处理，平均每批 7–15 个，但每个请求的耗时基本不降。P4 并发 256 时每批 14.6 个，一批约 2.5 s，折合每个请求 171 ms，和单独处理一个请求差不多（Derived）。
     - 所以 code2wav 是计算受限的，合批省不了时间（Hypothesis：要用 profiler 确认时间花在 flow 还是 HiFT 上）。
   - **S1:7**：只有一个 thinker，它最先饱和。并发 128 时 TTFT 中位数 1.0 s，256 时 6.3 s。
5. **换节点结果可以复现**（Measured）。
   - compute-03 上，S2:6 闭环最高 19.86 请求/秒，第一批节点是 19.72 和 19.39。开环到 23.8 请求/秒仍然全部满足 SLO。
   - R8 闭环最高 18.71，SLO 容量 16.8。
6. **过载时的失败**（Measured）。
   - **R8 显存不足**：开环 24 请求/秒及以上，R8 出现服务端 CUDA 显存不足，每档有 31–314 个请求失败，但服务没有退出。
     - 报错信息显示，同一张卡上另外两个进程分别占了 35 GiB 和 9 GiB，报错的进程只有 2.8 GiB，过载时没有余量。
     - 报错的是哪个阶段没有直接记录。同时出现的 cuFFT 错误说明很可能是 code2wav（Hypothesis）。
     - 其他布局没有这个问题。
   - **压测客户端句柄用完**：32–40 请求/秒时，客户端的文件句柄用完了，报 "Too many open files"。登录节点上的软上限是 1024，计算节点上没有直接查。出错时同时在途的请求有八百到一千多个，与这个上限吻合。
     - 这是测量工具的问题，只出现在已经超过 SLO 容量的速率上，不影响容量结论。
     - 下一批会把客户端的软上限调高（在硬上限以内）。

### 2.5 对小 batch 实时服务意味着什么

- **放置方式只影响吞吐上限，不影响低负载时的延迟**（Measured）。如果目标是小 batch 实时服务，选哪种布局应该由峰值负载决定。
- **要降低小 batch 延迟，只能在单个请求的串行路径上下功夫**（Derived）：
  1. **每个 token 少读字节**：量化 thinker 的权重。
  2. **一次读权重产出多个 token**：投机解码。
  3. **把 thinker 切到两张卡上**：TP=2，每张卡只读一半权重。在 NVLink 对上，all-reduce 开销小。
  4. **talker 和 code2wav 流式启动**：降低首段音频时间。
- 这些作为第三批的候选，见第 6 节。

**每种布局的等待点**：

- **thinker 独占 GPU 时（S2:6、P4）**：
  - 合批几乎不增加每 token 的时间。S2:6 的 thinker 从有效 batch 4 到 25，每 token 从 29 ms 只涨到 34 ms（Measured）。
  - 这正是大模型解码在 batch 不大时受带宽限制的特征：同一次读权重可以服务更多请求（Derived）。
- **thinker 和 talker、code2wav 同卡时（R8）**：
  - thinker 每 token 从 32 ms 涨到 81 ms，而有效 batch 只有 1 到 10（Measured）。
  - 涨幅来自同卡上其他进程抢 GPU 时间，而不是 batch 变大（Derived）。对比 S2:6 在 batch 25 时也只要 34 ms。
- **等待从并发 128 起移到 code2wav（S2:6、P4）**：
  - S2:6 并发 256 时，code2wav 中位数 5.6 s，约是 e2e（9.1 s）的 61%（Measured）。
  - thinker 的排队到并发 256 才出现：p90 347 ms，中位数仍只有 6 ms。

### 4.2 code2wav 的实际批大小（服务端日志，Measured）

| 布局 | 并发 16 | 并发 64 | 并发 128 | 并发 256 |
|---|---|---|---|---|
| S2:6 每批平均请求数 | 1.06 | 1.32 | 3.76 | 6.86 |
| P4 每批平均请求数 | 1.07 | 2.37 | 7.84 | 13.47 |
| R8 每批平均请求数 | 1.00 | 1.21 | 1.67 | 6.30 |

- **配置上限**：sglang-omni 给 code2wav 设的上限是每批 16 个，不等待凑批（`max_batch_size=16`、`max_batch_wait_ms=0`）。P4 并发 256 时，常常就是满的 16 个。
- **单位耗时的估算**（Derived）：在队列一直不空的时候，用相邻两批的间隔来估算每批的耗时。
  - P4 并发 128 时，每批 9.8 个，折合每个请求 190 ms；并发 256 时，每批 14.6 个，折合每个请求 171 ms。
  - 小 batch 时，单独处理一个约 14 s 语音的请求是 140–190 ms。
  - **合批基本不省时间**（Derived），所以 code2wav 的吞吐大约固定在每进程 5–6 请求/秒。
  - **R8**：code2wav 还要和 thinker 抢卡，并发 256 时折合每个请求 279 ms。
- **这意味着**（Hypothesis）：大 batch 下真正限制容量的是 code2wav 的计算量，以及它和 talker 共用的 GPU。
  - 要提高容量，可以给 code2wav 单独的 GPU，或者让 code2wav 更快（比如减少 flow 的步数、用更快的 vocoder 实现）。
  - 时间到底花在 flow 还是 HiFT 上，要看 profiler，见第 7 节。

## 6. 第三批候选：投机解码、流水线、量化、拆分

下面按第 2–4 节的数据，估计每个方向最多能省多少。这里只是计划，还没有在 A6000 上验证能不能跑。

| 方向 | 针对 | 数据给出的上限（Derived） | 在 sglang-omni 520b49ee 里的现状 | 建议 |
|---|---|---|---|---|
| 量化 thinker 权重（INT8/INT4，只量化权重） | 小 batch 延迟 | thinker 生成约占 e2e 的 60%，每 token 受带宽限制。权重字节减半，thinker 的时间最多减半，e2e 最多省约 30% | 由 SGLang 负责。sglang-omni 只为 Qwen3-Omni 加了适配，MiniCPM-o 的 thinker 能否加载量化权重要先试 | 先在单卡上做功能检查，再测小 batch |
| thinker TP=2（NVLink 对） | 小 batch 延迟 | 每卡只读一半权重。每步多两次 all-reduce/层，NVLink 对上开销小。thinker 每 token 有望从 26 ms 降到 15 ms 左右（Hypothesis） | Qwen3-Omni 用过 `--thinker.tp_size 2`，MiniCPM-o 待查 | 和量化对照测 |
| 投机解码 | 小 batch 延迟 | thinker 生成约占 e2e 的 60%。若每次读权重平均接受 2 个 token，e2e 最多省约 30% | 执行层直接拒绝，调度器固定关闭 | 只在纯 SGLang 上测 thinker 语言模型作为参考，单独报告 |
| 流式流水线 | 首段音频时间 | 现在首段音频 = e2e（1.5–2.6 s）。talker 按块启动后，首段音频可以降到“thinker 前几块 + talker 第一块 + code2wav 第一块” | MiniCPM-o 不支持。Qwen3-Omni 支持流式和 `enable_partial_start` | 用 Qwen3-Omni 测（原计划 E2） |
| code2wav 拆到独立 GPU | 大 batch 吞吐 | 大 batch 时 code2wav 占 e2e 六成，并且和 talker 抢卡 | code2wav 已经是独立进程，可以单独指定卡号 | 低成本，可以先做：比如 2 个 thinker、4 个 talker、2 个 code2wav 卡 |
| prefill/decode 拆分 | 大 batch | 各档 prefill 只有 26–84 ms，不到 e2e 的 3%，收益很小 | 有显式的 prefill/decode 调度角色，适用范围待查 | 放到最后 |

**后续（2026-11-18）**：“code2wav 拆到独立 GPU”已经在实验 7、9 里做了：同样 8 张卡，thinker 2 张、talker 2 张、code2wav 4 张（2+2+4）最好，短回答容量比 2+6 高约 7.5%（实验 9）。其余方向还没做。

## 7. 已知问题和局限

- **压测客户端的句柄上限是 1024**：只影响 32 请求/秒以上的过载档。下一批会在客户端启动时把软上限调高（在硬上限以内）。**后续**：已在 a89165f 修复（2026-11-17 00:35），4 倍速回放的重跑用的是修好的版本。
- **更正（2026-11-17）：第一批 S1:7 的 thinker 事件文件并没有缺。** 集群上文件完整。是从集群同步到分析机器时，我用了单文件 50 MB 的上限，这个 69 MB 的文件被漏掉了。同样被漏掉的还有第二批 B2l（S2:6、S4:4）和 G1 的 12 个文件，共 0.86 GB。现已补拷，受影响的 6 个实验已重新分析。
- **并发 1 的提示样本偏短**：负载生成器给每一档抽的提示不同，比较各档时要用归一化的指标。
- **code2wav 的时间包含它内部的排队**：服务端事件里，code2wav 的“处理时间”是从派发到完成。
- **还没做的分析**：
  - **更正（2026-11-17）：torch profiler。** 第一批 R8 和 S2:6 在并发 64 的 trace 并不大（每个文件约 50 KB），而且里面只有 CPU 事件，没有 GPU kernel。各阶段进程的日志都报了 `CUPTI initialization failed … CUPTI_ERROR_INVALID_DEVICE`：那台机器是 570 驱动加 cuda-compat，CUDA 13 的 CUPTI 起不来。compute-03（580 驱动）上的补测已经录到 GPU kernel，分析放在 `research/` 的实验 1。这部分要回答两个问题：S2:6 的 thinker 卡为什么只有 60–80% 采样利用率；code2wav 的时间花在 flow 还是 HiFT 上。
  - **开环的阶段分解**：AOH 开环没有记录服务端事件，所以没有按速率的阶段分解。
  - **后续（2026-11-18）**：GPU kernel 级的分析见实验 1（第二版）和实验 5；code2wav 的时间拆解见实验 6（每个请求约 0.2 秒 GPU 计算，合批不省）。
