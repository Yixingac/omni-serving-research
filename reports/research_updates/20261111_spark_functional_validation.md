# 阶段报告：DGX Spark 上的功能验证（2026-11-11）

> 本报告的数字全部来自个人 DGX Spark（GB10，统一内存，ARM64），**只用于验证功能，不能与 A6000 的结果比较**。样本量很小（每个并发级别 4–8 个请求），只报告中位数。

## 为什么先在 Spark 上做

实验室的 A6000 作业（Job 409712）要到 19:19 才开始。为了让作业一开始就能产出有效数据，我们先在 Spark 上把同一套软件（相同的 sglang-omni、sglang、torch 版本）跑通：服务能否启动、客户端和 trace 是否正确、服务端事件能否按 request_id 对齐、分析与报告能否从原始数据自动生成。

## 做了哪些运行

| 运行 | 内容 | 结果 |
|---|---|---|
| s1（run01） | MiniCPM-o 4.5 `--text-only` | **失败**：缺少 `onnx`（sglang-omni 的 `minicpm-o` 可选依赖），服务无法启动 |
| s1（run02） | 同上，补装依赖后 | 成功：服务 170 秒就绪；W1 文本 smoke 3 个、并发 1/4 各 8 个，全部成功 |
| s2 | MiniCPM-o 4.5 默认语音流水线（单卡） | 成功：服务 250 秒就绪；W3b 文本→语音 smoke 2 个、并发 1/2 各 4 个；小规模 Agent 4 个会话 |
| s3 | 与 s2 相同，thinker `mem_fraction_static` 0.85→0.6 | 成功：服务 155 秒就绪 |
| s4 | 改进后的 Agent、用 MiniCPM-o TTS 生成语音提问、语音 Agent | 成功：服务 150 秒就绪；生成 26 个素材（12 段语音提问、2 段朗读、12 个视频）；文本 Agent 9 个会话、语音 Agent 4 个会话 |

## 观察到的事实（Measured，GB10）

1. **A6000 环境也缺同一个依赖。** s1 的失败暴露出两套运行环境（Spark 和 Unicorn）都没有安装 `onnx`。如果没有在 Spark 上先跑，Job 409712 里所有 MiniCPM-o 实验都会在服务启动时失败。两边已补装，实验执行器在启动服务前检查必需的模块。
2. **文本服务正常，输出合理。** W1 的三个回答都是对输入笔记的两句话总结。并发 1 时 TTFT 中位数约 0.12 秒，每个请求约 77 个输出 token，端到端约 5.2 秒（约 15 token/s）。这与 GB10 的内存带宽量级相符：8B BF16 权重约 16 GB，按约 273 GB/s 计算，每秒最多读约 17 遍。
3. **语音输出不是流式下发的。** 文本逐块到达，但每个请求的音频只有一个块，在请求结束时整段到达。因此对这个模型，“首个音频块时间”等于整段语音生成完成的时间。
4. **三个阶段对同一请求是串行的。** 服务端事件显示：thinker 生成完整段文本后，talker 才收到输入（传递约 2 毫秒），talker 结束后 code2wav 才开始。s2 中位数：thinker 执行约 3.65 秒、talker 约 1.15 秒、code2wav 约 0.19 秒（n=11）。
5. **默认显存配比会让 code2wav 跳过 CUDA graph，但在这里没有测出影响。** 默认配置下，thinker 启动时占用了剩余内存的 85%，之后 code2wav 发现余量只有 2.2 GB，跳过了 Flow 模型的 CUDA graph。把 thinker 的占比降到 0.6 后不再跳过，但 code2wav 中位耗时几乎不变（193.4 vs 194.1 ms，n=11）。
6. **Agent 协议需要容错。** 第一版 Agent 只有 2/4 个会话答对。模型的实际回复里有：把工具参数写成字符串、在同一条回复里同时给出工具调用和猜测的答案、把工具名当作键并在一条回复里调用两个工具。改为接受这些写法、并行执行多个工具调用后（s4），文本 Agent **9/9** 答对，库存类任务每一步并行调用两次工具；语音 Agent（语音提问、语音回答）**3/4** 答对。
7. **语音和视频输入路径可用。** 合成视频的圆数（W4）两次都答对（5 个）。语音提问直接要求回答数字（W2）时两次都答错（481→100、377→12）：这些题需要心算多位数乘法，不调用工具时模型答不对；同样的语音题交给带工具的 Agent 时 3/4 答对，说明音频本身被正确理解。W2 作为负载用来测延迟，正确率不作为模型能力的结论。

## 这些结果对 A6000 实验的影响

- 第 3、4 条说明：在这个版本上，语音延迟主要取决于 thinker 生成完整文本的时间。拆分部署（把 talker 放到另一张卡）不会让单个请求的语音更早开始，但可能在多请求并发时减少 thinker 和 talker 争用同一张卡。A6000 上的 x7b 会检验这一点。
- 第 5 条的对照在 A6000 上复核（x3m），因为 48 GB 显存比 Spark 紧张得多。
- 第 6 条的改进已进入 A6000 的 Agent 实验（x5）。s4 的两个 trace 已作为公开示例放在 `examples/traces/`。

## 局限
